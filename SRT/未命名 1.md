## 2. 把 SRT 从“解释框架”压成“研究程序”

一个理论想走出闭门造车，关键不是它是否宏大，而是别人能不能拿它开工。

你接下来最该做的是把 SRT 改写成 3 条明确研究程序：

### A. 公理化程序

目标：让数学、理论物理、理论认知方向的人知道你不是纯比喻。

你需要明确：

- 最小对象是什么
- 允许的操作是什么
- 哪些量是定义，哪些量是推论
- 哪些命题是公理，哪些是定理，哪些只是启发性解释

尤其你现在要严控一个问题：  
**不要把“哲学主张、数学结构、跨尺度类比、经验解释”混写在同一层。**

这会直接影响别人是否把你当“可工作的理论”还是“高密度思想文本”。

### B. 预测程序

目标：让外部人相信 SRT 不只是重新命名已有东西。

你至少要形成 2 类预测：

- **区分型预测**  
    SRT 与 FEP、IIT、算法理想主义、过程哲学相比，到底在哪些情形下给出不同判断。
- **操作型预测**  
    给出一个可测指标、一个估计方法、一个数据场景、一个对照基线。

一句话说：  
你要把 SRT 从“能解释很多”推进到“在某个场景下比别的框架更早、更准、或更统一”。

### C. 原型程序

目标：让 AI / 复杂系统 / 认知科学的人有可跑的入口。

现在最适合你的不是大实验，而是 **一个小而硬的 toy model**。  
比如：

- regime shift / change-point detection
- continual learning 中任务边界的 Fisher 谱变化
- 多稳态系统里的“稳定化阈值”
- 分类边界形成中的选择代价变化

这里的原则很简单：  
**先做一个别人能复现的小模型，不要一上来试图证明宇宙观。**

# 一、目前最值得优先修的，是“规范源冲突”

这是最影响最小漂移和最小幻觉的。

最明显的一个例子：

这对 AI 来说是一个非常危险的信号：

- 一个文件说 canonical 是 `_SRT_D_VALUE_CANONICAL.md`
- 另一个治理协议却说 canonical 锚定是 `AI/SRT_AI_01_Ontology.md`

这类冲突会直接带来三种后果：

- 模型在不同上下文里抓不同“权威源”
- 生成时把旧定义和新定义混写
- 为了自洽而自动脑补过渡逻辑，幻觉风险上升

## 这一类问题要怎么修

你应该做一轮 **canonical source audit**，重点不是找理论错误，而是找：

- 哪些文件仍引用旧 canonical
- 哪些治理文件还写着过时锚点
- 哪些 split/compact/bridge 仍然偷偷承担规范功能

### 最优做法

把所有核心概念统一成这种形式：

- `canonical_id`
- `canonical_path`
- `deprecated_aliases`
- `last_promoted_from`
- `supersedes`

然后让：

- `CANONICAL_REGISTRY.md`
- `_SRT_MANIFEST.yaml`
- 各治理协议

都只从这一个规范表派生。

这些都很好，但还不够直接。

## AI 更需要这种硬标记

建议在 frontmatter 加一个字段：

ai_role: canonical | compact_core | bridge | navigation | archive | historical | deprecated  
ai_priority: 1 | 2 | 3 | 4 | 5  
ai_read_before: [...]  
ai_do_not_use_for_definition: true/false

这样模型或者检索代理可以立刻知道：

- 哪些能当定义源
- 哪些只是导览
- 哪些不能用于最终回答

这个优化对“最小幻觉”非常有效。

# 七、Manifest 现在应该升级成真正的“单一机器真源”

`_SRT_INDEX.md` 里已经写了“机器可读清单请参考 `_SRT_MANIFEST.yaml`” 。  
这是非常对的方向。

但从你现在能看到的其他文件关系来看，manifest 还没有完全成为唯一真源。  
因为：

- index 有自己的入口清单
- navigation map 有自己的入口清单
- canonical registry 也有自己的入口判断
- explanation protocol 甚至还留着旧 canonical

这说明 manifest 还更像“一个辅助清单”，不是“主控制器”。

## 最优状态应该是

manifest 直接包含：

- file path
- id
- title
- ai_role
- canonical_of
- supersedes
- layer
- epistemic_layer
- claim_mode
- token_estimate
- stable_summary
- read_priority
- do_not_use_for_definition
- depends_on

然后由脚本自动生成：

- navigation map 的一部分
- index 的一部分
- canonical registry 的一部分
- AI start file 的 reading order

只要做到这一步，读取成本、漂移、幻觉都会明显下降。

# 八、你的解释协议很好，但需要从“写作规范”升级成“抽取规范”

`_SRT_EXPLANATION_PROTOCOL.md` 现在已经要求：

- Mechanism
- Falsification
- Boundary  
    这对减少混乱非常有帮助 。

但它更像“作者写作约束”，还不完全是“AI 抽取约束”。

## 建议再补一个“机器抽取头”

每个核心条目最前面都固定加：

[Canonical Claim]  
[Operational Scope]  
[Evidence Level]  
[Not to be inferred]  
[Primary Dependencies]

因为 AI 在长文里最容易犯的错不是没看到公式，  
而是把下面几件事混成一件：

- 规范定义
- 机制解释
- 候选类比
- 外部比较
- 暂未证实的扩展

你现在协议里有这个精神，但还没压成最适合机器提取的头部格式。

# 九、最该压缩 token 成本的，不是所有文档，而是“入口高频文件”

从成本角度看，你最该动刀的是这几个：

- `STATUS.md`
- `SRT_Navigation_Map.md`
- `_SRT_INDEX.md`
- `CANONICAL_REGISTRY.md`
- `SRT_Quick_Start.md`

原因很简单：  
这些最容易被代理反复读取。  
每次读取它们太长，费用就会被入口层吃掉，而不是花在理论正文上。

## 建议

对这几个文件都做一个 “AI-lite 版”：

- `STATUS_AI.md`
- `SRT_NAV_AI.md`
- `_SRT_INDEX_AI.md`
- `CANONICAL_REGISTRY_AI.md`

它们只保留：

- 当前有效定义源
- 当前入口顺序
- 当前废弃源
- 当前高优先文件

这比让模型每次都啃完整大文件便宜太多。
