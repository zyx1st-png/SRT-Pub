# Part 02: 这一类问题要怎么修

> Source owner: [`../未命名 1.md`](../未命名%201.md)
>
> Reading-aid guardrail: this shard is a connector-safe navigation copy. It does not create new definitions, new claim status, or independent authority.

## 这一类问题要怎么修

你应该做一轮 **canonical source audit**，重点不是找理论错误，而是找：

- 哪些文件仍引用旧 canonical
- 哪些治理文件还写着过时锚点
- 哪些 split/compact/bridge 仍然偷偷承担规范功能

### 最优做法

把所有核心概念统一成这种形式：

- `canonical_id`
- `canonical_path`
- `deprecated_aliases`
- `last_promoted_from`
- `supersedes`

然后让：

- `CANONICAL_REGISTRY.md`
- `_SRT_MANIFEST.yaml`
- 各治理协议

都只从这一个规范表派生。

---

# 二、你现在最大的成本问题，不是正文，而是“入口层太重”

这点非常明显。

`SRT_Navigation_Map.md` 已经做得很细，覆盖：

- entry layer
- Chinese core text family
- two-axis reading map
- domain paths
- longform split navigation
- annex navigation
- canonical registry layer
- governance layer
- operations layer
- experimental paths
- topic indexes 

`_SRT_INDEX.md` 也同样非常重，既有维护说明、入口、registry、layer 解释、更新记录、治理入口、板块入口，又有大量链接清单 。

这对人类也许还好，因为人会挑着看。  
但对 AI 来说，问题是：

- 入口文件 token 很贵
- 目录说明占了很多上下文
- 真正的理论最小骨架被大量导航文本淹没
- 模型很容易把“导航语句”当成“理论正文的一部分”

## 你的优化方向

你现在需要的不是再多一个导航文件，而是把入口层压成三级。

### Level 1：机器首读入口

只保留最少内容，目标是 **500–1200 token 以内**。

内容只放：

- theory one-liner
- 三域定义一句话版
- canonical source table
- reading order
- do-not-use files
- stable file classes

这应该是专门给 AI 的入口，不给人类铺陈。

比如叫：  
`SRT_AI_START.md`

### Level 2：人类导航入口

也就是现在 `SRT_Navigation_Map.md` 这种，但应更偏人类。

### Level 3：全量索引

也就是 `_SRT_INDEX.md`，保留长尾导航和治理信息。

换句话说，现在缺的不是更多导航，而是：

**把“人类导航”和“AI 入口”分开。**

# 三、你已经有“compact core”，但还缺“AI compact core”

你现在的 compact core 是按板块做的，这很好。  
比如 Physics、AI、Neuroscience 都已经有 compact core 入口，`CANONICAL_REGISTRY.md` 也反复强调 compact core 固定最短主线、长文负责展开和沉积 。

但这还不等于 AI 最优可读。

因为 AI 最常见的问题不是读不懂单篇长文，而是：

- 不知道先读哪 3 个文件
- 不知道哪些文件是规范层，哪些只是展开层
- 不知道哪些旧文不能再当定义源

## 所以你还缺一个东西

不是按学科板块的 compact core，  
而是按“全仓库最小理论闭包”的 compact core。

建议你单独做一个：

`SRT_MINIMAL_CANON.md`

只包含：

- 总命题
- L0 / L1 / L2 最小定义
- `Ĝ_θ` 最小定义
- `Ψ_f` 最小定义
- `d-value` 最小定义
- `T_dir` 最小定义
- 哪些只是桥接，不是主张
- 哪些是实验下注，不是本体定义

长度最好控制在 **1500–3000 token**。

这会极大降低 AI 读取费用，因为很多问题根本不需要先扫 Navigation Map + Index + Registry + Glossary。

---

# 四、Glossary 现在方向对，但还不够“检索即定义”

你已经把 glossary 拆成了：

- 核心符号
- 数学记号
- 领域参数
- 关键概念
- 假设索引
- 位置索引与新增术语  
    而且明确说拆分版用于导航与检索，总表保留为历史完整总表 。

这一步是对的。  
但从 AI 角度，还可以再优化两步。

## 问题1：Glossary 更像“目录”，还不是“最小判定器”

AI 其实最需要的不是术语很多，而是每个核心术语都能快速回答：

- 是什么
- 不是什么
- 归属哪层
- canonical 在哪里
- 常见混淆是什么

## 建议

每个核心词条加统一头部：

Term:  
Canonical path:  
Layer:  
Epistemic layer:  
One-line definition:  
Not equivalent to:  
Common confusions:  
See also:

这样 AI 检索一个词条时，几乎不需要再去看长文。

## 问题2：没有显式“废弃术语映射”

如果你历史写作中改过术语，AI 很容易把旧词和新词混起来。

## 建议

增加一个：  
`Glossary/SRT_Glossary_07_Deprecated_Aliases.md`

专门写：

- 旧称
- 新称
- 废弃原因
- 何时废弃
- 兼容说明

这会明显减少旧稿污染。

---

# 五、Index 里混了太多“状态日志式增量”，这对 AI 不友好

`_SRT_INDEX.md` 里虽然已经说“主索引仅保留导航/入口/注册信息，以提升可维护性与 AI 检索稳定性” ，  
但实际上它仍然带有不少：

- 最近更新说明
- 核心新增文件批次
- 同期 Core 层修正
- 历史增量说明

这些内容对人类是有价值的，  
但对 AI 来说，它们会造成一个问题：

**模型会把“最近改了什么”错当成“理论现在是什么”。**

## 建议

把 `_SRT_INDEX.md` 再瘦一刀，只做：

- 入口
- 注册表
- 路由
- 板块骨架

把更新内容全部挪到：

- `CHANGELOG.md`
- `Governance/_SRT_CHANGELOG_2026.md`
- release notes

不要在 index 再混“更新叙事”。

---

# 六、需要给 AI 明确“哪些文件不该优先读”

这是现在结构里比较缺的一点。

你已经在多个地方写了：

- split 只负责导航，不替代 canonical 定义 
- 某些原版中文文本不再承担唯一主入口角色 
- 历史主文保留为历史入口而非当前唯一主文 

这些都很好，但还不够直接。

## AI 更需要这种硬标记

建议在 frontmatter 加一个字段：

ai_role: canonical | compact_core | bridge | navigation | archive | historical | deprecated  
ai_priority: 1 | 2 | 3 | 4 | 5  
ai_read_before: [...]  
ai_do_not_use_for_definition: true/false

这样模型或者检索代理可以立刻知道：

- 哪些能当定义源
- 哪些只是导览
- 哪些不能用于最终回答

这个优化对“最小幻觉”非常有效。

---

# 七、Manifest 现在应该升级成真正的“单一机器真源”

`_SRT_INDEX.md` 里已经写了“机器可读清单请参考 `_SRT_MANIFEST.yaml`” 。  
这是非常对的方向。

但从你现在能看到的其他文件关系来看，manifest 还没有完全成为唯一真源。  
因为：

- index 有自己的入口清单
- navigation map 有自己的入口清单
- canonical registry 也有自己的入口判断
- explanation protocol 甚至还留着旧 canonical

这说明 manifest 还更像“一个辅助清单”，不是“主控制器”。

## 最优状态应该是

manifest 直接包含：

- file path
- id
- title
- ai_role
- canonical_of
- supersedes
- layer
- epistemic_layer
- claim_mode
- token_estimate
- stable_summary
- read_priority
- do_not_use_for_definition
- depends_on

然后由脚本自动生成：

- navigation map 的一部分
- index 的一部分
- canonical registry 的一部分
- AI start file 的 reading order

只要做到这一步，读取成本、漂移、幻觉都会明显下降。

---

# 八、你的解释协议很好，但需要从“写作规范”升级成“抽取规范”

`_SRT_EXPLANATION_PROTOCOL.md` 现在已经要求：

- Definition
- Formalization
- Mechanism
- Falsification
- Boundary  
    这对减少混乱非常有帮助 。

但它更像“作者写作约束”，还不完全是“AI 抽取约束”。

## 建议再补一个“机器抽取头”

每个核心条目最前面都固定加：

[Canonical Claim]  
[Operational Scope]  
[Evidence Level]  
[Not to be inferred]  
[Primary Dependencies]

因为 AI 在长文里最容易犯的错不是没看到公式，  
而是把下面几件事混成一件：

- 规范定义
- 机制解释
- 候选类比
- 外部比较
- 暂未证实的扩展

你现在协议里有这个精神，但还没压成最适合机器提取的头部格式。

---

# 九、最该压缩 token 成本的，不是所有文档，而是“入口高频文件”

从成本角度看，你最该动刀的是这几个：

- `STATUS.md`
- `SRT_Navigation_Map.md`
- `_SRT_INDEX.md`
- `CANONICAL_REGISTRY.md`
- `SRT_Quick_Start.md`

原因很简单：  
这些最容易被代理反复读取。  
每次读取它们太长，费用就会被入口层吃掉，而不是花在理论正文上。

## 建议

对这几个文件都做一个 “AI-lite 版”：

- `STATUS_AI.md`
- `SRT_NAV_AI.md`
- `_SRT_INDEX_AI.md`
- `CANONICAL_REGISTRY_AI.md`

它们只保留：

- 当前有效定义源
- 当前入口顺序
- 当前废弃源
- 当前高优先文件

这比让模型每次都啃完整大文件便宜太多。

# 十、你现在最值得做的 8 个优化动作

按优先级排，我建议这样做：

## P1

修 canonical source 冲突。  
尤其先修 `d-value` 这类规范源不一致问题：`CANONICAL_REGISTRY.md` 与 `_SRT_EXPLANATION_PROTOCOL.md` 必须统一

## P2

新增一个 `SRT_AI_START.md`。  
专供 AI 首读，极短，明确：

- 理论最小骨架
- canonical 源
- 阅读顺序
- 禁止误用文件类型

## P3

新增一个 `SRT_MINIMAL_CANON.md`。  
把 SRT 最小理论闭包压成单文件。

## P4

给 manifest 增加 `ai_role / ai_priority / do_not_use_for_definition / token_estimate` 字段。

## P5

给 frontmatter 增加 `ai_role` 体系。

## P6

把 `_SRT_INDEX.md` 进一步瘦身，把更新叙事挪走。

## P7

给 glossary 增加“标准词条头”和“deprecated aliases”表。

## P8

把 navigation/index/registry 的可生成部分尽量交给 manifest 自动派生。

# 最后一句判断

你当前仓库的主要问题，不是“AI 不可读”，而是：

**它已经进入“治理足够强，但入口层太贵、规范层开始出现局部自相矛盾”的阶段。**

这其实是好事。  
因为说明你已经不是从无到有的问题，而是从“能用”到“高效、低漂移、低幻觉”的优化问题。

下一步最值得做的，不是再抽象讨论，而是直接落文件。  
我建议先从两个东西下手：

**`SRT_AI_START.md`** 和 **canonical source audit 清单**。
