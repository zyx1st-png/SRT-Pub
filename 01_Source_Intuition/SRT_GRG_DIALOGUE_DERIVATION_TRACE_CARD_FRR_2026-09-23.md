# GRG Grammar Card derivation trace — FRR fusion case

## 0. Purpose

This file preserves the substantive assistant-visible analysis that led from the FRR focused reading to the current experimental GRG Generative Grammar Card v0.2.

It is a structured reconstruction of the dialogue's explicit analytical content, not a hidden chain-of-thought record.

The author explicitly accepted the Card derivation as a bounded package on 2026-09-23; see the companion author-adjudication record.

## 1. Starting problem

The initial aim was not to create a universal GRG schema by introspection.

The aim was:

`take one mature external relational framework -> reconstruct it source-first -> see where the existing GRG representation breaks -> modify the Card -> repeat with other domains`.

FRR was useful because it already contains rich source-native machinery around:

- local contextualization;
- potential / probable organization;
- Boolean compatibility;
- actualization;
- objective incorporation;
- later conditioning / global formation;
- recoherence / gluing.

This creates strong overlap pressure without granting identity.

## 2. First failure exposed: “selection” is overloaded

The first important correction was that a Card field named simply `selection` is too coarse.

A source can contain several operations that sound like selection:

- choosing or fixing a context;
- excluding incompatible relations;
- filtering;
- assigning probabilities;
- negative selection;
- source-native self-determination.

None of those is automatically SRT Selection.

Therefore the Card needs to decompose the pre-occurrence region before asking whether an actual event qualifies as SRT Selection.

The provisional chain became:

`open generative structure -> localization/context -> proxy/cut -> distinction/equivalence -> reach/compatibility -> Selection-burden landscape -> actual event -> Selection audit -> consequence -> retention`.

The key guard is:

> rich candidate-space organization is not yet SRT Selection.

## 3. Second failure exposed: actualization was being used ambiguously

The dialogue identified two distinct questions:

1. How does the source tell us that an event/fact/process is actual?
2. Does the source explain why that actuality occurs?

These are not the same burden.

A theory may provide a strong actuality criterion while explicitly presupposing occurrence.

Therefore the Card needs:

- `actuality_criterion`;
- `occurrence_account_status`.

Recommended occurrence statuses:

`explained | constrained | probabilized | presupposed | open | not_applicable`.

This prevents GRG from filling a source-level explanatory gap by vocabulary substitution.

## 4. Third failure exposed: Selection was drifting into a causal “extra step”

Earlier dialogue wording sometimes suggested:

`Selection -> Actualization`.

That is unsafe because SRT currently treats Selection as genuine actualised non-neutral differentiation, not as an extra force that then causes actualization.

The cleaner research representation is:

`L0/open generative structure -> pre-occurrence organization -> Selection/Actualization event -> consequence`.

Selection and actualization are treated as two analytical aspects of one occurrence:

- actualization = actuality status;
- Selection = actuality viewed as genuine non-neutral differentiation.

This is not a canonical rewrite. It is a Card-level guard against inventing a new collapse-like mechanism.

## 5. Anti-tautology problem was narrowed

The hard question remained:

> if Selection is actualized non-neutral differentiation, how can the programme distinguish genuine Selection from arbitrary descriptive change without merely repeating the definition?

The dialogue narrowed the burden by separating:

- causal explanation of why an actuality occurs;
- individuation / membership conditions for when an actuality counts as Selection.

SRT need not necessarily solve the former in every domain to avoid total circularity, but it must pay the latter burden.

A provisional Selection audit therefore emerged with four pressures:

### 5.1 Occurrence / actuality

The source domain must independently support that something actual occurred.

GRG cannot certify actuality merely because its own schema has a field for it.

### 5.2 Event individuation

The event boundary cannot be manufactured arbitrarily by changing temporal or descriptive resolution.

The Card should record how the source individuates an event, transition or process unit.

### 5.3 Relational non-neutrality

The actualized difference must matter to the source-native relational organization at the declared position.

Pure relabeling or an equivalent representation is insufficient.

### 5.4 Representation invariance

The claimed difference should survive legitimate structure-preserving redescription.

A coordinate change or variable rename should not manufacture a new Selection.

These criteria remain research-level and provisional.

## 6. Non-neutrality was decomposed

The dialogue then separated three senses of non-neutrality that had previously been conflated.

### 6.1 Ontological non-neutrality

Actual is not equivalent to merely potential / probable / modelled.

This is the minimum actuality-side asymmetry.

### 6.2 Relational non-neutrality

At a declared finite position, two descriptions or states are not safely substitutable with respect to source-native constitutive relations, constraints or individuation conditions.

This motivates an explicit equivalence / neutrality field in the Card.

### 6.3 Historical / generative non-neutrality

Some actualities continue to alter later generative conditions.

This is retention / sedimentation, not a prerequisite for Selection occurrence.

Therefore:

`Selection occurrence != retention / sedimentation`.

Terminal Selection remains conceptually possible even when later retained efficacy is absent.

## 7. Neutrality mapping became a central Card function

A useful reorganization emerged from the proxy discussion.

A proxy does not merely “compress information”.

A proxy provisionally determines which lower-order differences can be treated as equivalent for the current research or Selection burden.

In analytical shorthand:

`D -> D / ~_P`.

This led to the working idea that a GRG Card should record not only differences but:

- what is treated as equivalent;
- under what declared position/context;
- why that equivalence is licensed;
- what consequences would invalidate it.

This is more precise than a generic “compression” field.

## 8. Proxy role was retyped

The dialogue accepted the following research-level guard:

> proxy organizes Selection burden, but does not replace Selection.

The Card therefore needs to ask:

- what distinctions the proxy exposes;
- what distinctions it flattens;
- whether the flattening is source-native or analyst-imposed;
- whether suppressed distinctions retain a reopening path;
- whether the proxy changes reach / routing / support.

This also avoids conflating a GRG generative proxy with the repository's measurement / operational proxy vocabulary.

## 9. Reach was refined through the neutrality view

Reach was sharpened from “how far an influence propagates” toward:

> the ability of a distinction to remain or regain relational non-neutrality across one or more proxy / equivalence transformations and enter consequence-producing paths.

This supports a Card block that records:

`difference -> pathway -> later consequence / Selection loop`

rather than forcing an early scalar reach score.

The dialogue also preserved:

- active reach;
- latent reconstructive reach;
- reopening paths.

## 10. Reconstructibility had to split into two layers

FRR contains source-native routes from local / coarse Boolean organization toward richer compatible structures.

That source-native structural reopening cannot simply be relabeled GRG reconstructibility.

The Card therefore needs:

### 10.1 Structural reopening path

What does the source itself permit?

Examples can include gluing, recoherence, re-expansion, reconstruction, reconfiguration or another source-native operation.

### 10.2 Generative reconstructibility

Does the GRG representation preserve enough provenance, alternative cuts and failure information that the current higher-order compression can later be reopened and recut?

The first is source-native.

The second is a GRG methodological / normative burden.

## 11. Dual reconstructibility was exposed

Once the Card itself was recognized as a higher-order proxy, a second-order problem appeared.

There are two compression loops:

### 11.1 World-facing compression

A domain mechanism or proxy compresses worldly differences.

### 11.2 Theory-facing compression

GRG compresses source-theory differences into cross-domain relational roles.

Therefore a robust Card should preserve:

- reconstructibility from a current domain proxy back to lower-order source/world distinctions;
- reconstructibility from a GRG abstraction back to the source-native mechanism and theory.

This is why provenance is part of the Card's generative architecture rather than merely bibliography.

## 12. Non-identity guards became mandatory

Cross-domain fusion easily produces accidental identity claims.

FRR made this visible.

The Card must therefore contain a specific non-identity block.

Candidate statements from the FRR case:

- Boolean frame != GRG proxy automatically;
- negative selection != SRT Selection automatically;
- germ != GRG objectification automatically;
- recoherence != GRG reconstructibility automatically;
- global-in-formation != SRT L2 automatically.

A mapping can be useful at the level of role without claiming ontological identity or shared mechanism.

## 13. Analogy, mapping, instantiation and transfer were separated

The dialogue developed a stricter progression:

`analogy -> explicit mapping -> candidate instantiation -> tested instantiation -> transfer candidate`.

Definitions:

- analogy = structural resemblance;
- mapping = declared correspondence;
- candidate instantiation = source mechanism appears to satisfy a GRG operational role;
- tested instantiation = the role survives source-native pressure / negative controls;
- transfer candidate = a learned generative expectation is carried to another case and tested there.

The Card should record the current status rather than treating all resemblance as instantiation.

## 14. Anti-metaphor test

A central admission test emerged:

> if replacing source-native terms with GRG terms changes no expectation, diagnostic boundary, failure condition, intervention sensitivity or transfer burden, then the mapping is merely redescriptive.

This does not mean every useful Card must already produce a novel empirical prediction.

It means GRG vocabulary must do some analytical work beyond renaming.

## 15. Higher-order formation field was added but kept bounded

The wider dialogue developed criteria for distinguishing:

- aggregation;
- objectification;
- load-bearing proxy;
- new Selection position.

For the Card core, only the bounded diagnostic is retained:

- is the higher-order structure merely a descriptor?
- does it change reach / routing / support?
- can it generatively re-enter later relations?
- does it create a new load-bearing organization for later Selection?

More speculative developments such as endogenous perspective, bearer, self, subjectivity and civilization are not inserted into the core Card. They are parked in a separate downstream package.

## 16. Generative expectation became a required Card field

The Card should ask:

> if this mapping is correct, what nontrivial pattern should later appear?

This can concern:

- reach;
- compatibility;
- failure;
- re-opening;
- support;
- transition structure;
- intervention response.

The expectation must be fallible.

A grammar that can redescribe every outcome after the fact is not mature.

## 17. Failure / recut condition became equally important

For every positive mapping, the Card should record:

> what would force this mapping to be revised, reopened or rejected?

This creates an anti-self-sealing route.

Possible outcomes include:

`retain | revise | reopen | reject_mapping | insufficient_evidence`.

Failure is a legitimate Card result.

## 18. Empty fields became informative

A fusion case should not be forced to populate every GRG category.

An empty field can mean:

- source structure absent;
- source evidence insufficient;
- mapping not licensed;
- category not applicable;
- Card overfit to earlier cases.

Repeated empty fields across heterogeneous cases may force Card simplification.

This is one of the main mechanisms by which fusion cases can change GRG rather than merely decorate it.

## 19. Resulting Card architecture

The resulting experimental Card v0.2 contains twenty blocks:

1. source identity;
2. native event ontology;
3. open generative structure;
4. localization / context;
5. proxy / cut / compression;
6. equivalence / neutrality;
7. reach / compatibility;
8. Selection-burden landscape;
9. Selection audit;
10. occurrence account;
11. consequence;
12. retention / L2 candidate;
13. higher-order formation;
14. reconstructibility;
15. generative expectation;
16. failure / recut condition;
17. anti-metaphor test;
18. mapping status;
19. non-identity guard;
20. provenance / reconstruction + Card outcome.

The executable template is stored separately in Operations/Templates.

## 20. Why the next cases are fusion cases, not adversarial tests

The dialogue originally used “pressure test” and briefly described evolution as an “enemy” or adversarial case.

The author corrected this framing.

The forward route should treat later domains as **fusion cases** in the same spirit as FRR.

The case does not exist to defeat GRG.

It exists to provide source-native structures that may:

- instantiate part of the Card;
- expose false equivalence;
- leave fields empty;
- force field splitting;
- force field removal;
- create new fields;
- alter generative expectations;
- recut the Card itself.

The desired loop is:

`fusion case -> source reconstruction -> Card application -> mismatch / gain -> Card revision -> cross-card reconciliation`.

## 21. Current stop boundary

This derivation does not:

- create GRG v0.4;
- close the anti-tautology problem;
- define a universal cross-domain ontology;
- authorize canonical edits;
- authorize BCTB T2;
- promote downstream subjectivity / civilization analysis into the core Card.

Those are separate burdens.
