# G0/T1 prospective resource-budget amendment

**Discussion draft only. `DRAFT / NOT EFFECTIVE`; not approved and not an execution authorization.** This proposal addresses the missing historical `T_PS-A` by asking for a prospective, synthetic-only resource gate and separately fixed absolute G0/T1 budgets. Until an independent review and researcher decision adopt a dated amendment, the preregistered §6.1 gate remains in force and both biological G0 and T1 remain **RESOURCE NO-GO**.

This proposal changes only how resource feasibility is established. It does not change graph construction, exchange proposals, Louvain settings, fixed seeds, sample/window selection, outcome definitions, NC classifications, statistics, failure rules, or biological data access boundaries. It authorizes no NC-0 freeze, G0/T1 null generation, or result inspection.

## Evidence boundary

The accompanying NC-0a closure report records the source checks and SHA-256 ledger. The final bounded search found no run-4 termination event. The reconstruction is closed for now: the progress-supported 71.560963 h is a partial elapsed-time sum; 76.630770 h is a conditional mixed-source estimate that assumes an unverified run-4 endpoint and compatible duration clocks. Neither is a valid `T_PS-A`. This amendment does not relabel either number as a baseline.

The **NC-0a synthetic battery PASS** at the locked HEAD: 16 synthetic cases, 128 chains, 44,937,216 proposals, 16,000 BFS-oracle proposals and 48 comparisons passed their registered checks. It retains `MIXING-UNRESOLVED`. **The full Gate NC-0a is not passed / remains NO-GO because the primary G0 resource criterion is unmet.** The run used 4,352.529 s accounted wall and 17,356.060 s accounted process-group CPU on the M1 Pro. It did not run 200 Louvain trials on every G0 null graph, does not reproduce the G0 graph-size/workload distribution, and cannot establish G0 or T1 runtime.

For a nonbinding, size-stratified reference, the saved NC-0a per-case `worker_process_cpu_seconds` values were divided by each case's eight-chain proposal count (eight chains × 32E proposals). The 16 case records are hash-linked in the public audit summary; the formal battery summary SHA-256 is `affd8b32c907aac930a80ce640137afbc9c182d990adc4d8f2108f464c9902c5`. At the four measured sizes, family-specific mean costs were 12.49, 36.78, 130.14 and 489.50 CPU microseconds per proposal at N=100, 340, 1150 and 3900. At each measured N, take the four-family minimum, median and maximum; linearly interpolate those three per-proposal values in N (no extrapolation) onto the ten registered finite N values, then weight by 4,900 null tasks per N and `4E=32N` proposals per task. This gives about **129 / 151 / 155 CPU-hours** (low / median / high family-cost interpolation) for the swap-chain worker component. The `worker_process_cpu_seconds` numerator is child-process CPU after the chain pool; it includes chain checkpoint metrics and local audits but excludes parent-side graph construction and the later BFS oracle. This is not a pure kernel timing and the between-family range is not a confidence interval. It excludes H3, null-graph serialization, 200 Louvain trials per G0 graph and actual G0 topology. At ideal four-core saturation that component alone corresponds to about 32–39 wall hours; real scheduling and other stages increase it. This sensitivity calculation is not a bound or G0 prediction.

[Claude's independent review](https://github.com/zyx1st-png/SRT-Pub/pull/1114#issuecomment-6294714756) gives a separate, deliberately coarse **120–210 wall-hour** order-of-magnitude for full G0 at four workers (about 5–9 continuous days). This is retained as a planning reference only; neither it nor the NC-0a size reweighting is a validated prediction, confidence interval, completion guarantee or approved budget. The historical `T_PS-A` is not substituted or repaired by either estimate.

No new biological null outputs were inspected for this draft. Resource counts below are the registered workload ledger, not a reanalysis of biological outcomes.

## Prospective synthetic benchmark path

All benchmark work uses a separate engineering seed namespace, never formal G0/T1 seeds. It must not inspect or use new biological null outputs. The executor, runtime, source identity, strata, task order, recovery rule and every numerical parameter below must be independently reviewed and frozen before the first timing. A benchmark interruption is recorded and charged; it is not silently restarted under a larger cap.

1. **Freeze the inventory and profile weights.** Let `s=(N,k)` index the 10 registered finite N values and 10 deterministic profile medoids at each N. Within each N, scale the frozen profile features by the median and IQR of its 490 source graphs, assign each source graph to the nearest PAM medoid by robust-scaled mean absolute L1 distance (ties go to the lower fixed medoid index), and let `M_s` be the number assigned to stratum `s`. Derive `base_plan_sha256` from canonical JSON of the frozen plan with `base_plan_sha256`, medoid seeds/assignments and bootstrap seeds omitted; for each N, set the PAM seed to `int.from_bytes(SHA256(ascii("G0_T1_PROFILE_MEDOIDS_V1|" + base_plan_sha256 + "|" + N))[:8], "big")`. Hash the exact PAM implementation/version and resolve equal-distance assignments by source-manifest ID. Require `M_s≥1`, `Σ_k M_(N,k)=490` for each N, and `Σ_s M_s=4,900`. Candidate source-to-medoid tolerance is distance ≤2.0 in these median/IQR units; any source beyond it means the 100-stratum representation is inadequate and timing does not start. The number of primary null tasks represented by `s` is `W_s=10 M_s`, hence `Σ_s W_s=49,000`. Thus the 100 stratum weights are the manifest-derived `10M_s`; they need not be equal to one another, and balanced benchmark sample counts are never workload weights. Verify `E_i=8N_i` for every original graph and compute the proposal total from actual `E_i`; do not use `1,797,712,000` unless every graph passes that check.

2. **Fix the nested calibration sample.** A bootstrap unit is one parent graph fixture together with all **10** independently seeded 4E null tasks generated from that graph. Each child includes all 200 fixed-seed Louvain trials. Keep the 10 child cost vectors as one cluster throughout sampling and scheduling; never bootstrap the ten children as independent observations. Candidate core sample: 12 independently seeded parent fixtures per stratum, 8 training and 4 fixed holdout. Freeze all parent IDs, seeds, family assignments and the holdout split before timing. For each stratum, choose the primary one of the four existing synthetic graph families before timing by minimum robust-scaled L1 distance to that stratum's source medoid over the frozen structural features, after exact N/E/degree-histogram checks and the declared tolerances; ties use the fixed family order in the hashed plan. In distance scaling, use the same per-N median/IQR values estimated from the complete source-feature census in step 1; a zero-IQR feature contributes zero to distance but remains in exact-match and support checks. If no family can meet the match rule, stop before timing and retain NO-GO. A family is a stress condition, not a random draw from the biological workload, so it receives no invented mixture weight.

   The initial core calibration therefore contains 1,200 parent clusters and **12,000** child null tasks: 8,000 training tasks / 1,600,000 Louvain trials and 4,000 holdout tasks / 800,000 Louvain trials. The 4 holdout parent clusters per stratum are fixed before timing and remain sealed until the training sample size and model are finalized. They are never used to choose profiles, fit cost models, select families, trigger expansion, tune thresholds or enter the bootstrap. For each training size `m∈{8,12,16}`, calculate leave-one-parent-cluster-out predictions `x̂_sj=mean(x_s,−j)` from the other `m−1` training blocks. For each resource metric, the weighted absolute relative-error diagnostic is `A_CV=Σ_s M_s·mean_j(|x_sj−x̂_sj|/x_sj)/Σ_s M_s`; for each N, one-sided underprediction is `U_CV,N=Σ_{s:N}M_s·mean_j(max(x_sj−x̂_sj,0))/Σ_{s:N}M_s·mean_j(x_sj)`. These training-only diagnostics are evaluated separately for complete parent-block CPU seconds and worker-service wall seconds (source-build costs are excluded). They determine expansion: add exactly four new training clusters per stratum if `A_CV>20%`, any `U_CV,N>25%`, or the bootstrap `U95/median>1.25` for either null-task CPU total or total worker-service wall. The ratio is computed before adding fixed source-build/serial costs and before recovery, so constants cannot hide task-cost dispersion. Use the prehashed seed list; stop at 20 training clusters. If a criterion still fails at 20, return RESOURCE NO-GO. At that maximum, core calibration contains 2,400 parent clusters and 24,000 child tasks / 4,800,000 Louvain trials. No expansion or model change may be selected after opening holdout results or inspecting scientific Q values.

3. **Add a separate structural-tail stress panel.** Before timing, within each N sort the 490 source graphs by each frozen cost-risk descriptor, breaking ties by canonical source-manifest ID; select the first and last `ceil(0.10×490)=49` source IDs for each of degree CV, normalized maximum degree, leaf fraction, absolute assortativity, triangle density, bridge-edge count and articulation-node count. Let `D_N` be the deduplicated union of those actual source IDs; publish the IDs, feature vectors, and fixed seeds before timing. Do not replace a selected source profile with its PAM medoid. For every `i∈D_N` and each of the four synthetic families, generate one stress fixture that matches the source's exact N, E and degree histogram and is within 2.0 per-feature robust median/IQR units of its frozen feature vector (a zero-IQR feature must match exactly); ties and generator search order follow the hashed plan. If any selected source-family pair cannot meet that rule, retain RESOURCE NO-GO rather than dropping the source or family. Run one fixed-seed 4E child task with all 200 Louvain trials per matched fixture. This is a structure-by-family panel; seed-to-seed variability remains represented by the 10-child core parent clusters. It contributes at most 19,600 stress tasks and 3,920,000 Louvain trials (`|D_N|≤490` across ten N values); these tasks have no workload weights and never enter model fitting. Compare each stress task's CPU/service-wall cost and Louvain work counters with the maximum single-child training value in the same N/profile cell, and apply the frozen post-4E feature-support gate below. This tests observed source-feature extremes without claiming that a synthetic fixture reproduces the full biological graph or the unobserved null tail.

4. **Measure the complete graph and task paths.** In the frozen target environment, time and hash all 4,900 original graph reconstructions from the verified source files, including load/window preparation, correlation, MST, top-edge selection, identity checks and the selected cache writes. This stage creates no null graph or new Q outcome. Include each measured source-build cost once in the G0 schedule; an H3 cache entry reused by G0 is not rebuilt or charged twice. Measure the distinct H3 reference/Q replay separately as a prerequisite cost and show it in the combined pre-NC-0 campaign ledger, not inside the G0-only prediction; if the approved execution sequence actually places that replay in the G0 authorization window, report both G0-only and combined totals explicitly. Each null-child cost vector records process-tree CPU and worker-service wall for 4E proposals, connectivity/BFS, 200 Louvain trials, invariant/metric checks, lossless trace encoding/compression, result writes, checkpoints, fsyncs, hashing and worker/coordinator overhead. Record the actual operational cost drivers: swap accept/reject reasons and BFS vertices/edges visited; pre/post-4E triangle/clustering, assortativity, edge overlap, bridges/articulation and degree summaries; and, for every Louvain trial, optimizer passes/levels, node moves, nodes/edges scanned where instrumentable, trial CPU/wall and peak memory. Do not use Q values as predictors. Separately measure recorder overhead on five paired largest-N engineering fixtures with the same graph/task seeds and schedule, recorder on versus off; these dedicated fixtures are outside training and holdout but count against the benchmark cap. Require median CPU and worker-service-wall overhead ≤10%, and use recorder-on full-task costs in every prediction. If iteration/move counters or full task timings cannot be recorded, the tail model is unvalidated and resource GO is blocked.

   The exact production task DAG and four-worker dispatcher must be frozen before timing. Candidate order is the canonical source-manifest order followed by null replicate ID; each source's ten children become eligible only after that source build and identity check. Model real serial stages (manifest/ledger, source-cache commit, compression, final verification), dependency waits and worker dispatch using the same scheduler implementation as the formal executor. For reproducibility, worker ties are resolved by worker index and simultaneous task completions by canonical task ID. A different scheduler or queue policy invalidates the wall prediction and requires rerunning the affected benchmark.

5. **Compute a cluster-bootstrap predictive distribution, not a confidence interval for a mean.** For each bootstrap replicate `b=1…10,000` and each stratum `s`, perform a two-level cluster resample. First draw `m` parent-block indices with replacement from the `m` training clusters, forming an outer empirical cost model. Then draw exactly `M_s` parent-block indices with replacement from that outer multiset; each inner draw contributes its intact 10-child vector. The outer resample represents uncertainty from the limited number of timed parent fixtures; the inner resample represents variation across the `M_s` fixed source assignments and ten engineering-seed tasks per source. Never resample child tasks independently. `M_s` is the number of actual source graphs assigned to the stratum, so the replicate represents `10M_s` of the 49,000 fixed null tasks; the benchmark's balanced fixture counts never become workload weights. Order source IDs within each stratum by the frozen manifest, map the inner draw sequence to those IDs in order, and map its ten child vectors to each source's fixed replicate IDs 1–10. This makes the nested draw and production dependencies reproducible while including finite-training-sample uncertainty.

   For each stage and stratum, the training estimate is the componentwise mean of the final `m` training parent-block vectors. Define each training residual block as `r_sj = x_sj − mean_train(x_s)`; a bootstrap draw uses `mean_train(x_s)+r_sj`, equivalently the original intact block `x_sj`. The ten child rows and all stage components remain together. The fixed holdout estimate for parent `j` is the training-only mean; holdout residuals `e_sj = x_sj − mean_train(x_s)` are revealed once and used only for the predeclared calibration/underprediction checks in step 6. They are never used to fit a cost relation, inflate U95, select a family, choose features or seeds, or enter the bootstrap. A failed holdout is RESOURCE NO-GO; it is not repaired by refitting or expanding on holdout data. There is no separate regression model: costs are estimated by frozen stratum and measured stage, with cluster resampling representing within-stratum source/task variability.

   For replicate `b`, define G0 campaign base process-tree CPU-hours as `C_b^base=(Σ_i C_build,i + Σ_{i,r} C_task,b,i,r + C_serial)/3600`. `C_task` includes the complete 4E/200-Louvain null task, audit, compression, write, checkpoint and worker-local work; `C_serial` includes coordinator/ledger, cache commit, queue/monitor and final verification CPU. Sum CPU for every process in the supervised tree once, including helpers, with no overlap between stage counters. Define the one-resume loss reserve `R_b^CPU` as the four largest costs in the combined eligible-work set `{C_build,i}∪{C_task,b,i,r}` plus measured watchdog restart, revalidation and ledger-reconciliation CPU; `C_b^plan=C_b^base+R_b^CPU/3600`. Source builds become reusable only after atomic write and identity/hash verification; if interrupted before that point, an in-flight build may be repeated once and is covered by this reserve. Completed verified builds are retained. Add the distinct H3 prerequisite CPU as a separate measured ledger item; if it shares a source build/cache with G0, count the shared build once.

   Generate base end-to-end wall `W_b^base` by discrete-event simulation of the frozen production DAG and actual dispatcher using each sampled task's measured **worker-service wall**, exact per-source build durations, measured serial-stage durations, source-build dependencies, four workers and queue/monitor overhead. Map clusters to canonical source IDs in manifest order for one schedule. Also simulate a conservative comonotone schedule: within each stratum sort measured source-build wall durations and sampled parent-block total service-wall durations descending, pair by rank (ties by canonical ID), then dispatch under the same DAG. Set `W_b^base` to the larger of these two makespans. Generate `W_b^plan=(T_b^base+R_b^wall)/3600` wall-hours, where `T_b^base=3600×W_b^base` seconds and `R_b^wall` is the sum of the four largest measured/sampled service-wall durations in the combined eligible-work set (all source-build jobs plus all null-task jobs) and measured watchdog restart, revalidation and ledger-reconciliation wall. At most four jobs are in flight in the four-worker pool, so this covers either a source build or null task interrupted in each slot. It deliberately reserves a worst-case one-time loss without assuming the interruption occurs at a favorable point. If the production executor interleaves builds and children, preserve that dependency and order in both base schedules. This is not `CPU/4` and does not substitute summed task wall for a schedule. Persist both event schedules, exact mappings, per-stage samples, bootstrap RNG seed and simulator/executor hashes so another analyst can reproduce both distributions.

   Serialize the frozen plan without its derived hash or bootstrap seed as UTF-8 JSON with sorted keys, separators `(",", ":")`, `ensure_ascii=True`, `allow_nan=False` and no trailing newline. Let `seed0=int.from_bytes(SHA256(canonical_plan_bytes)[:8], "big")`; use `PCG64(SeedSequence([seed0,m]))` for each training size `m` and exactly 10,000 replicates. Within each replicate, visit strata by ascending N then medoid index; draw outer indices in training fixture-ID order and then draw inner source-cluster indices in canonical source-manifest order. The JSON encoding, included keys, traversal order and integer byte order are frozen in the hashed plan. Define the null-task stability totals `C_b^null=Σ_{i,r}C_task,b,i,r/3600` CPU-hours and `S_b^null=Σ_{i,r}T_service,b,i,r/3600` worker-service hours, before source-build/serial additions and recovery.
