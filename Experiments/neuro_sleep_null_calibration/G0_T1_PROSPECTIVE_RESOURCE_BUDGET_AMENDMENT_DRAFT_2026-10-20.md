# G0/T1 prospective resource-budget amendment

**Discussion draft only. `DRAFT / NOT EFFECTIVE`; not approved and not an execution authorization.** This proposal addresses the missing historical `T_PS-A` by asking for a prospective, synthetic-only resource gate and separately fixed absolute G0/T1 budgets. Until an independent review and researcher decision adopt a dated amendment, the preregistered §6.1 gate remains in force and both biological G0 and T1 remain **RESOURCE NO-GO**.

This proposal changes only how resource feasibility is established. It does not change graph construction, exchange proposals, Louvain settings, fixed seeds, sample/window selection, outcome definitions, NC classifications, statistics, failure rules, or biological data access boundaries. It authorizes no NC-0 freeze, G0/T1 null generation, or result inspection.

## Evidence boundary

The accompanying NC-0a closure report records the source checks and SHA-256 ledger. The final bounded search found no run-4 termination event. The reconstruction is closed for now: the progress-supported 71.560963 h is a partial elapsed-time sum; 76.630770 h is a conditional mixed-source estimate that assumes an unverified run-4 endpoint and compatible duration clocks. Neither is a valid `T_PS-A`. This amendment does not relabel either number as a baseline.

The **NC-0a synthetic battery PASS** at the locked HEAD: 16 synthetic cases, 128 chains, 44,937,216 proposals, 16,000 BFS-oracle proposals and 48 comparisons passed their registered checks. It retains `MIXING-UNRESOLVED`. **The full Gate NC-0a is not passed / remains NO-GO because the primary G0 resource criterion is unmet.** The run used 4,352.529 s accounted wall and 17,356.060 s accounted process-group CPU on the M1 Pro. It did not run 200 Louvain trials on every G0 null graph, does not reproduce the G0 graph-size/workload distribution, and cannot establish G0 or T1 runtime.

For a nonbinding, size-stratified reference, the saved NC-0a per-case `worker_process_cpu_seconds` values were divided by each case's eight-chain proposal count (eight chains × 32E proposals). The 16 case records are hash-linked in the public audit summary; the formal battery summary SHA-256 is `affd8b32c907aac930a80ce640137afbc9c182d990adc4d8f2108f464c9902c5`. At the four measured sizes, family-specific mean costs were 12.49, 36.78, 130.14 and 489.50 CPU microseconds per proposal at N=100, 340, 1150 and 3900. At each measured N, take the four-family minimum, median and maximum; linearly interpolate those three per-proposal values in N (no extrapolation) onto the ten registered finite N values, then weight by 4,900 null tasks per N and `4E=32N` proposals per task. This gives about **129 / 151 / 155 CPU-hours** (low / median / high family-cost interpolation) for the swap-chain worker component. The `worker_process_cpu_seconds` numerator is child-process CPU after the chain pool; it includes chain checkpoint metrics and local audits but excludes parent-side graph construction and the later BFS oracle. This is not a pure kernel timing and the between-family range is not a confidence interval. It excludes H3, null-graph serialization, 200 Louvain trials per G0 graph and actual G0 topology. At ideal four-core saturation that component alone corresponds to about 32–39 wall hours; real scheduling and other stages increase it. This sensitivity calculation is not a bound or G0 prediction.

[Claude's independent review](https://github.com/zyx1st-png/SRT-Pub/pull/1114#issuecomment-6294714756) gives a separate, deliberately coarse **120–210 wall-hour** order-of-magnitude for full G0 at four workers (about 5–9 continuous days). This is retained as a planning reference only; neither it nor the NC-0a size reweighting is a validated prediction, confidence interval, completion guarantee or approved budget. The historical `T_PS-A` is not substituted or repaired by either estimate.

No new biological null outputs were inspected for this draft. Resource counts below are the registered workload ledger, not a reanalysis of biological outcomes.

These readings cannot establish safe G0 memory or disk capacity. NC-0a sampled about 490 MiB process-group RSS on a different workload; that is not a G0 peak estimate. On macOS, sampled RSS, `ru_maxrss`, system free-memory percentage and swap growth are monitoring signals, not a hard memory limit. A short-lived peak between samples can be missed, and the OS may disrupt the runner or other applications before a poll. The resource amendment must retain this risk explicitly.

The preregistered disk condition is projected temporary storage below 70% of baseline available free disk. At the snapshot above that is about 32.47 GiB. For a personal laptop, this proposal additionally recommends retaining at least 30 GiB free on the internal Data/VM container during the run; together those conditions would allow at most about 16.39 GiB of new G0 output at the measured baseline, before safety margin and unrelated system writes. This 30-GiB reserve is a proposed additional safety condition, not an already approved G0 threshold.

The previous 16-byte-per-proposal estimate is a naive record sensitivity (28.76 GB / 26.79 GiB), not a required format. Candidate lossless replay audit: for every proposal store the two selected edge ranks in the canonically sorted current edge list, orientation bit, and a result/rejection code (accepted, shared endpoint, invalid/duplicate edge, or disconnected rejection), packed to the minimum fixed width for that N. Given E=8N, this is 3 bytes per proposal at N=100, 4 bytes at N=150–1,725, and 5 bytes at N=2,600/3,900; across the registered size counts the uncompressed event stream is approximately 8.19 GB (7.63 GiB), before headers/checksums. Add seed, starting labeled-edge hash, implementation/runtime hash, per-reason totals, proposal totals, accepted-swap totals, rolling SHA-256 over canonical event bytes, final edge hash and optional compressed final edge list. Replay hash-selected streams through the exact implementation and a full-BFS acceptance oracle; store all 200 Q values and optimizer seeds. Chunked lossless compression (candidate pinned zstd version/level) can reduce storage, but its ratio and CPU cost are unknown until measured; buffer writes and fsync by fixed chunks, never per proposal.

This format **does satisfy the literal §3 “record all kernel attempts” requirement only if each proposal’s selected edges/orientation and decision code are losslessly present in the replay stream and the replay validator proves exact reconstruction**. Counts plus a rolling hash alone do not satisfy that wording. If the chosen implementation stores only seeds/counts/digests, §3 would need an explicit, prospectively reviewed amendment; this draft does not silently treat a digest as a complete trace. Measure compression size, read/replay time, hash validation and recorder CPU/wall overhead before selecting the final format.

Other preliminary uncompressed storage arithmetic, conditional on E=8N and uint32 node IDs: all 49,000 final null edge lists about 3.60 GB; the 4,900 cached original edge lists about 0.36 GB; 9.8 million float64 Q values about 78.4 MB. Combined with the 8.19-GB packed attempt stream this is roughly 12.23 GB (11.39 GiB), excluding sidecars, metadata, temporary copies, filesystem overhead and unrelated system writes. Candidate G0 output cap: 14 GiB plus at most 1 GiB temporary space, with at least 30 GiB free throughout; this would require roughly 45 GiB free at baseline and must also pass the preregistered `<70% of baseline free disk` rule. The prior 46.39-GiB point snapshot is not a current preflight and gives limited margin for unmeasured overhead. If exact retained files exceed the cap or the volume reserve, stop; do not drop attempts or loosen the rule. Consider a separately verified volume or a prospectively reviewed storage-policy revision.

## Preconditions and graph-identity calibration

No representative G0/T1 benchmark may start until the formal G0 executor exists and has been independently reviewed against §§2–6, including the exact 4E kernel, all 200 Louvain trials, complete attempt audit, checkpoints, failure/recovery behavior and output schema. The complete target runtime must also be locked: Python 3.14.0 and the pinned original `python-louvain` 0.16 semantics required by H3, plus exact NumPy/SciPy/NetworkX, BLAS/OpenMP settings, compiler/OS and serialization/compression dependencies. The NC-0a Python 3.11.15 runtime and its timings are not a substitute for that environment. Hash the executor, dependency lock, runner image/host, benchmark plan and graph/data manifest. A benchmark before these are fixed measures a different implementation and must be repeated.

The source of workload strata is the **reconstructed original observed graph set**, not archived job metadata alone: the 6,006 archived job summaries contain no edge lists. Using the SHA-256-verified S3 source files, archived realized neuron indices, exact source builder, state windows and frozen runtime, reconstruct the 4,900 original finite-N graphs and extract only resource-profile features (N, E, degree histogram/CV, leaf fraction, maximum degree, assortativity and predeclared connectivity/bottleneck summaries). Do not read new biological null output or use observed Q values to define strata. Hash the graph identities and feature inventory. Verify `E=8N` per graph before using the proposal total.

The required H3 panel is a separate identity and calibration point: reconstruct its fixed **120 original graphs** (6 recordings × 10 finite N × 2 states), run the preregistered original-Q identity replay with all 200 Louvain trials where available, and record graph-build, correlation/MST/top-edge, optimizer and audit costs by N. This is original-graph identity work, not a new null ensemble or new biological null result. The H3 panel validates runtime transfer to observed graph structure but represents only 120 of the 4,900 G0 source graphs; it does not replace the 4,900-graph feature census or synthetic null-task benchmark. The H3 graphs overlap the source-graph set: count their shared builder/cache work once in the G0 model and add only the distinct reference-path and identity-Q replay work. Missing historical trial-level comparators or failed identity checks remain NC-0 identity issues and cannot be repaired by this resource proposal.

G0 also pays to rebuild all **4,900 original graphs** from S3 before their 49,000 null tasks. Time the full registered path per matrix: load and prepare each exact (N,L) window, correlation matrix computation, maximum spanning tree and absolute-correlation top-edge selection, identity/hash checks, and cache writes. At N=3,900 a single dense float64 N×N matrix is 121,680,000 bytes (about 116 MiB); absolute-value, sorting/index and correlation work arrays can make active builder memory several times that amount, and the N×L input/workspace adds more. The often quoted ~0.3 GB per active builder is a planning estimate, not a measured peak. Measure four-worker aggregate RSS, host pressure and swap with real N,L dimensions represented by synthetic matrices. Candidate cache policy: build each original once, retain only canonical labeled edge lists, node/degree metadata and SHA-256 identity records (about 0.36 GB for 4,900 source graphs at E=8N and uint32 endpoints), and discard dense matrices after each build. Compare that measured one-time cache cost with recomputation; freeze one policy before resource prediction and execution. Do not place signal arrays or derived Q outcomes in the public repository.

## Prospective synthetic benchmark path

All benchmark work uses a separate engineering seed namespace, never formal G0/T1 seeds. It must not inspect biological null output. The benchmark is allowed only after the executor, runtime, source identity, strata and all parameters below are independently reviewed and frozen. An interrupted benchmark is recorded and charged; it is not silently restarted under a larger cap.

1. **Freeze source profiles and synthetic strata.** From the 4,900 reconstructed original-graph resource profiles, candidate design: within each of the ten registered N values, deterministically cluster the 490 source graph feature vectors into 10 medoids using PAM/k-medoids with robust median/IQR scaling, fixed feature order and a seed derived from canonical ASCII `G0_T1_PROFILE_MEDOIDS_V1|<base-plan-sha256>|<N>`. This gives 100 N×profile strata. For each medoid, create nonbiological fixtures matching its exact N, E and degree histogram; also match its leaf count and maximum degree, assortativity within ±0.05, and bridge/articulation counts within ±10% (preserve exact zero). Candidate generator search cap: 10,000 independent graph-generation attempts per fixture; if the feature tolerance is not met, stop and redesign before timing. Hash the feature list, medoid assignments, matching tolerances, graph generator, all benchmark seeds and task counts before timing.
2. **Fix repetitions and holdouts.** Candidate initial sample: 12 independently seeded synthetic fixtures per stratum, 8 training and 4 holdout, generated and hash-published before timing. Holdouts never enter model fitting. This is 1,200 full synthetic null tasks (240,000 Louvain trials, plus registered swaps), not biological null analysis. Expansion, if needed, adds exactly four training fixtures per stratum per round, leaves the four holdouts unchanged, and stops at 20 training fixtures per stratum. No seed, stratum or threshold can change after timing begins.
3. **Time the complete frozen path at four workers.** Include all 4,900 original graph correlation/MST/top-edge builds and cache writes, each null task’s 4E proposals and connectivity checks, 200 fixed-seed Louvain trials, topology/metric/invariant checks, per-attempt audit writes, checkpoints, lossless compression, fsync policy, hashing and permitted operational recovery. Measure stages separately and end-to-end: source graph build, swaps/connectivity, Louvain, audit/compression, storage and schedule. Time the 120 H3 graph identity replay separately, counting overlapping source-graph builds once and adding the distinct reference/Q work. Candidate audit-overhead test: five paired largest-N synthetic runs with the same fixed task/seed, recorder enabled and disabled. Candidate acceptance is ≤10% median CPU and wall overhead; retain the recorder in all prediction tasks. A code or format change after timing requires repeating affected stages.
4. **Capture tails and enforce the benchmark stop.** Record task wall and process-tree CPU, worker occupancy, accept/reject counts, Louvain iteration counts, sampled group RSS, host free memory/pressure, swap-used change, output bytes, peak temporary disk, rebuild time and all failures. Candidate benchmark cap: 24 cumulative wall-hours or 96 process-tree CPU-hours, four workers maximum, and the predeclared memory/pressure/swap/disk limits. Reaching either cap before coverage is **RESOURCE NO-GO**, with no extension.
5. **Predict and validate the full inventory.** Candidate method: 10,000 stratified bootstrap replicates over independent training fixtures and fixed holdout residuals, weighted by the hashed full-inventory task counts. Keep process-tree CPU separate from wall; model a four-worker schedule including 4,900 graph builds/cache, serial stages, writes/compression, queue imbalance and the frozen failure/recovery allowance. The one-sided 95th percentile (`U95`) is the candidate upper prediction for aggregate CPU and wall; also report the median and sensitivity to the highest-cost N/profile. Candidate acceptance: holdout aggregate wall and CPU error ≤20%, no N-specific underprediction >25%, and the measured H3 120-graph rebuild/Louvain totals within ±20% of their stage predictions. Any failed criterion or `U95 / median > 1.25` triggers only the fixed +4-training expansion; after the maximum, return NO-GO. The H3 panel is an observed-graph transfer check, not synthetic training data or a null outcome.
6. **Freeze the absolute cap and GO rule before first timing.** Candidate outer loss ceiling for the current four-worker laptop: 336 cumulative wall-hours (14 days) and 1,344 process-tree CPU-hours. This is rounded above 1.5× the coarse 210-hour wall reference (315 hours) and 1.5× its 840-CPU-hour full-utilization equivalent (1,260 CPU-hours). These are researcher decision candidates, not completion bounds. Candidate final G0 caps are `B_wall = 1.5 × U95_wall` and `B_cpu = 1.5 × U95_cpu`, rounded upward to the next whole hour; GO is possible only if both fit within the researcher’s dated, hash-recorded outer ceilings. If the ceilings are blank/rejected, predicted caps exceed them, uncertainty is unstable, validation fails or resource conditions do not fit, G0 is **RESOURCE NO-GO**. No biological output may be generated to decide whether a budget is acceptable.

Before any timing, the final review/commitment must explicitly fix each candidate value in the decision table below. A blank, unreviewed substitution or unapproved deviation means **NO benchmark / RESOURCE NO-GO**. The 1.5 factor, U95 method and numeric candidates are proposals, not active thresholds today.

## Candidate laptop safety conditions

These are proposed minimum controls for review, not current authorization:

- Keep at most four registered compute workers. Monitor the complete supervised process group, including helpers, and stop the group on watchdog/process-accounting failure.
- Keep separate cumulative wall and CPU-hour caps and per-task limits. Wall includes sleep and recovery intervals; every failed attempt consumes budget.
- Retain the preregistered RAM gate of peak measured memory below 80% of host RAM (12.8 GiB on this 16-GiB host), plus system free memory at or above 20%. Record aggregate process-group RSS and host pressure at fixed intervals. These are sampled conditions and do not enforce a hard cap.
- Record swap `total/used/free`, but do not use `free` as a predicted remaining budget. A candidate abort trigger is `swap_used` growth greater than 2 GiB from the fixed pre-run baseline, combined with pressure and volume-space readings; exact trigger semantics require independent review.
- Measure both internal Data and VM mount availability at baseline and continuously. Enforce both the existing `<70% of baseline available free disk` projection and, if adopted, the added 30-GiB internal reserve. Include output, checkpoints, failed attempts, temporary files, logs, swap pressure and safety headroom.
- Require AC power, normal available thermal/performance telemetry, and an active sleep assertion. A missing or unparseable required signal fails preflight. This does not protect against forced shutdown, OS failure or unobserved thermal throttling.
- Stop and classify incomplete work on any cap, watchdog, disk, power, sleep, integrity or accounting violation. Preserve the failed record and charge. Only frozen operational recovery may resume; scientific failures, statistical NO-GO and unknown classifications do not receive automatic retry.

The current snapshot has about 46.39 GiB free, but swap-used is already about 9.70 GiB and `pmset` returned no thermal status text. Those observations do not pass a future preflight by themselves. No files should be removed and no resource threshold should be lowered to make the current disk reading pass.

## Required independent decisions and stop conditions

Before this proposal can replace the `T_PS-A` gate, the independent reviewer must confirm that the historical gap is not being treated as zero, that the synthetic workload covers G0's actual computational cost drivers, and that the prediction and uncertainty method supports the proposed margin. The reviewer must also examine the measured output format and the non-hard macOS memory controls. The researcher then accepts or rejects numeric caps and remaining risks. Only after both steps may a dated, hash-bound amendment become effective.

**Automatic NO-GO conditions:** benchmark cap reached before adequate coverage; unstable or failed holdout/H3 prediction; inability to estimate the full 200-Louvain component or 4,900-source-graph rebuild/cache stage; estimated wall or CPU cap above the researcher's predeclared maximum; sampled memory/pressure or disk policy not met; actual result storage exceeds the approved reserve; loss of the lossless proposal trace; or any unresolved mismatch between the synthetic task and registered G0 work. A NO-GO cannot be changed after inspecting biological null results.

This proposal preserves the present state: `T_PS-A` unresolved, H2 historical reconstruction closed for this evidence set, G0 and T1 **RESOURCE NO-GO**, no new computation authorized.
