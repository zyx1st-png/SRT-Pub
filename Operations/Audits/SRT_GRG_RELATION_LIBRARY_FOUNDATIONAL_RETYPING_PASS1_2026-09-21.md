# GRG Relation Library foundational retyping — Pass 1

## 0. Purpose

This pass applies the new typed architecture to the live Relation Library.

Every current library item is classified as one or more of:

~~~text
HORIZONTAL-RECORD
VERTICAL-CORE
V-H-INTERFACE
COMPOSITE
EXPECTATION-LAYER
VALIDATION-MATURITY
PROXY / TRACE
~~~

## 1. R1 family

Current family:

~~~text
R1a retained imprint
R1b maintained scaffold
R1c causal re-entry
R1d prospective reuse / transfer
~~~

### R1a — retained imprint

Retyping:

~~~text
PROXY / TRACE / HORIZONTAL DIAGNOSTIC
~~~

Reason:

A retained imprint shows that history is readable in an objectified state or representation.

It does not by itself pay vertical historical efficacy.

Therefore:

~~~text
R1a != R-HIST
~~~

R1a is evidence that a candidate history-sensitive organization may exist.

### R1b — maintained scaffold

Retyping:

~~~text
V-H INTERFACE / FORMATION-MAINTENANCE CANDIDATE
~~~

R1b may represent a stabilized organization that supports later horizontal process.

But maintenance alone does not establish later causal re-entry.

Possible destination:

~~~text
R-FORM / maintenance burden
or
R-HIST precondition
~~~

depending on the final architecture.

### R1c — causal re-entry

Retyping:

~~~text
VERTICAL-CORE -> R-HIST-a
~~~

Admission:

~~~text
prior formed / retained organization
-> materially conditions later generation
~~~

This is the clearest current R1 contribution to the minimal vertical grammar.

RNN spectral NULL remains a failed mapping of one objectified causal candidate, not a rejection of the family.

### R1d — prospective reuse / transfer

Retyping:

~~~text
VALIDATION-MATURITY / EXPECTATION BURDEN
~~~

R1d is not another world-relation primitive.

It asks whether a relation identified in one context supports prospective transfer / reuse.

Therefore R1d should eventually move out of the relation-family decomposition and into relation maturity / E-B evaluation.

## 2. X3 family

Current split:

~~~text
X3a articulated / encoded generative expectation
X3b operative expectation regime
~~~

### X3a — articulated expectation

Retyping:

~~~text
HORIZONTAL / EPISTEMIC-PUBLIC OBJECTIFICATION RECORD
~~~

X3a is a representation / rule / protocol / schedule / model of expected future relation.

By itself it does not alter participant possibilities.

Therefore:

~~~text
X3a is not a core vertical relation
~~~

but it is important for the ontology/epistemology interface because it externalizes expectation into a public object.

### X3b — operative expectation regime

Retyping:

~~~text
V-H INTERFACE / COMPOSITE
~~~

X3b combines:

~~~text
externalized expectation object
+ maintenance / implementation
+ changed participant accessibility / action conditions
~~~

It is therefore not obviously primitive.

Likely decomposition:

~~~text
X3a representation
+ R-RECON or R-POS / C-MULTI
+ domain-specific enforcement mechanism
~~~

depending on the case.

Result:

X3b remains valuable as a recurring composite pattern, especially in institutions / technology / law, but should not currently be promoted to minimal vertical core.

## 3. X4 family

Current split:

~~~text
X4a reconstructed condition
X4b recursive reconstructed-field feedback
X4c inherited reconstructed condition
~~~

### X4a — reconstructed condition

Retyping:

~~~text
VERTICAL-CORE CANDIDATE -> R-RECON
~~~

This is the cleanest current expression of generative-condition reconstruction.

Admission still requires more than long-term effect.

### X4b — recursive reconstructed-field feedback

Retyping:

~~~text
VERTICAL-CORE / COMPOSITE -> R-RECON + later re-entry
~~~

X4b adds the return path:

~~~text
current process
-> reconstructs field F
-> F changes later process P
-> later P can further reconstruct F
~~~

This is a recursive strengthening of R-RECON, not necessarily a separate primitive family.

### X4c — inherited reconstructed condition

Retyping:

~~~text
COMPOSITE -> R-RECON + R-HIST / persistence-inheritance burden
~~~

X4c should not be treated as a primitive relation until inheritance is shown to require a distinct grammar burden rather than composition of reconstruction and retained efficacy.

## 4. Current library mapped to the new architecture

| Library item | New role | Minimal architecture destination |
|---|---|---|
| R1a | proxy / trace | objectification / evidence layer |
| R1b | V-H interface / maintenance candidate | R-FORM OPEN or R-HIST precondition |
| R1c | vertical core | R-HIST-a |
| R1d | maturity / expectation | E-B / transfer validation |
| X3a | horizontal public representation | objectification / expectation externalization |
| X3b | composite V-H interface | R-RECON / R-POS / C-MULTI + domain mechanism |
| X4a | vertical core candidate | R-RECON |
| X4b | recursive vertical composite | R-RECON + re-entry |
| X4c | inheritance composite | R-RECON + R-HIST |

## 5. Important consequence

The live Relation Library is currently mixing:

- world-relations;
- objectification records;
- proxy / trace status;
- maturity / transfer status;
- composite patterns.

That is acceptable for v0.1 provenance, but not for a mature grammar owner.

Therefore the next library schema should separate at least:

~~~text
relation_type
architecture_role
verticality_status
objectification_interface
composition_of
expectation_burden
maturity_status
~~~

rather than encode all of these in the relation name.

## 6. Proposed architecture-role field

Future records should use one or more of:

~~~text
UPSTREAM_CONSTRAINT
HORIZONTAL_REALIZATION
VERTICAL_CORE
VH_INTERFACE
COMPOSITE
EXPECTATION
NORMATIVITY
REFLEXIVE
PROXY_TRACE
VALIDATION
~~~

## 7. Proposed verticality declaration

Every mature relation record should state:

~~~text
research_question
stabilized_objectification
what_is_given
what_is_reopened
vertical_claim
horizontal_baseline
bridge_assumption
failure_condition
~~~

This answers the red-team concern that question-relative verticality could otherwise become a relabeling escape.

## 8. Consequence for current M3/M4

M3 and M4 remain valid maturity / transfer labels.

They should not be mistaken for relation types.

~~~text
M3 / M4 = validation status
not
horizontal / vertical architecture role
~~~

An X3b composite can be M3 without becoming a primitive GRG relation.

An R-RECON core candidate can be only M2 while still being architecturally more foundational.
