# GRG M3 / M4 cross-domain transfer + absorption audit — Pass 1

## 0. Trigger

After Relation Library v0.1:

~~~text
X3b = M2 / provisional cross-domain invariance
X4b = M2 / DOMAIN-LIMITED
M3 = NONE
~~~

The next gate required:

- an independently evidenced target for X3b beyond the existing institutional set;
- a genuinely non-biological X4b candidate;
- no M-status increase merely by adding examples.

## 1. Methodological correction: M3 != M4

The first transfer pass exposes a necessary distinction.

### M3

~~~text
independently evidenced relation match
~~~

M3 asks:

> Does a relation already frozen under source-native admission rules recur in an independently owned domain without semantic drift?

M3 does not require GRG novelty in the target domain.

### M4

~~~text
transfer-generating match
~~~

M4 asks a stronger question:

> Before target outcome / decisive source inspection, does GRG generate a useful target-domain variable, control, distinction or failure expectation that ordinary target-domain practice did not already supply in the same form?

Therefore:

~~~text
M3 recurrence
!=
M4 transfer gain
!=
scientific distinctiveness
~~~

This distinction should be explicit in the library and framework.

## 2. Selection-provenance limitation

Both relations were frozen before the target close-read.

But Kubernetes and Performative Prediction were not separately preregistered as targets before source search.

Therefore:

~~~text
eligible claim = M3 independent semantic/source match
strong prospective M4 claim = NOT ELIGIBLE
~~~

Even aside from this provenance limitation, both target fields already explicitly own the relevant distinction, so M4 would still be NO / ABSORBED.

## 3. X3b -> Kubernetes NetworkPolicy

Frozen X3b:

~~~text
expectation
+ operative embodiment
+ changed participant possibility relation
~~~

Target source:

~~~text
NetworkPolicy object
+ enforcing network plugin/controller
-> actual connectivity filtering
~~~

Source-native near-miss:

~~~text
NetworkPolicy object exists
+ no enforcing implementation
-> no traffic effect
~~~

Verdict:

~~~text
semantic invariance = PASS
independent evidence = PASS
negative-control structure = source-native PASS

X3b = M3 PASS
M4 = NO / ABSORBED
~~~

Why M4 fails:

Kubernetes already explicitly distinguishes API declaration from implementation/enforcement.

GRG adds no new Kubernetes control or mechanism.

The dependency direction is preserved.

Verdict:

## 5. X4b label revision

Cross-domain evidence now shows that the biological label is too narrow.

Programme-level rename:

~~~text
old generic label:
X4b recursive selective / viability feedback

new generic label:
X4b recursive reconstructed-field feedback
~~~

Biological specialization:

~~~text
selective / viability feedback
~~~

Machine-learning specialization:

~~~text
performative distribution feedback
~~~

Generic admission:

~~~text
A reconstructs typed conditioning field F
+
F changes later selection / viability / accessibility /
distribution / transition conditions on P
+
the mediation A -> F -> later P is source-native and evidenced.
~~~

Guard:

~~~text
generic "feedback" is insufficient.
F must be identified and both sides of the mediated dependency must be paid.
~~~

This is a noncanonical library refinement.

## 6. What GRG actually gains

GRG gains:

1. a cross-domain burden that survives mechanism change;
2. an explicit distinction between representation and operation;
3. an explicit mediated-field recursion that survives biology -> ML transfer;
4. a maturity model able to say "same grammar, no target-domain novelty".

GRG does not gain:

- Kubernetes networking theory;
- institutional theory ownership;
- performative prediction theory;
- machine-learning novelty;
- a universal feedback law.

## 7. Absorption is a successful outcome

Both target domains absorb the GRG question completely at M4.

That is not programme failure.

It demonstrates the intended architecture:

~~~text
mature source-native theory
can fully own the mechanism
while
GRG retains a constrained cross-domain relation record.
~~~

The framework should prefer this result to manufactured novelty.

## 9. Next gate

Do not immediately search for more M3 examples.

Next programme question:

~~~text
Can the frozen GRG library generate an M4 transfer?
~~~

Requirements for a legitimate first M4 attempt:

1. freeze relation and target domain before decisive target-source/outcome inspection;
2. write the target-domain question / variable / control / expected failure in advance;
3. compare against ordinary target-domain practice;
4. if the same distinction already exists, record ABSORBED / M4 NO;
5. if GRG changes the design, execute or source-test it without semantic drift;
6. preserve null / absorption results.

A first M4 attempt should be bounded and should not open a broad new deep well.
