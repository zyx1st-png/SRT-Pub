# GRG Cross-Objectification Anti-Drift Protocol v0.1

## 0. Purpose

This protocol blocks a recurring failure mode:

~~~text
GRG vocabulary
-> search domain for matching objects
-> score correspondences
-> mistake correspondence density for grammar evidence.
~~~

It also blocks the opposite failure mode:

~~~text
object mismatch is declared irrelevant
-> grammar retreats to a more abstract level
-> every outcome becomes "compatible"
-> GRG becomes self-sealing.
~~~

Both are prohibited.

## 0.1 Continuity-recovery Gate 0 — GRG is inside the audit

The 2026-09-23 dialogue recovery adds a precondition to all gates below.

Current GRG constructs are not exempt from the same objectification analysis applied to source domains.

Before a positive grammar candidate is named:

~~~text
relevant source cut
-> reconstruct why it exists / what it compresses

relevant GRG cut
-> reconstruct why it exists / what it compresses

then
-> compare / split / demote / delete / retain
-> run existing-owner semantic absorption
-> only then consider a new candidate
~~~

Required question:

> What does the source make us understand differently about why the current GRG cut was formed?

If the answer is only:

> “the source has something that looks like the GRG term”,

the audit has failed.

A case may validly conclude that the current GRG term is:

- too coarse;
- too broad;
- merely one source-local projection;
- already decomposed by existing GRG owners;
- unnecessary.

## 1. Gate A — research-question rewrite

If a case starts primarily with:

~~~text
"What is the GRG equivalent of X?"
"Which GRG object is Y?"
"Is domain term Z really reach / support / Selection / proxy?"
~~~

rewrite before proceeding.

Preferred form:

> What generative dependency is the source model organizing, and what changes when its unit / boundary / relation is recut?

Object mapping may return later as an audit.

## 2. Gate B — source-native readability

Before a GRG mapping claim, produce a source-native reconstruction that can be read without unexplained GRG terms.

Every load-bearing reconstructed relation must carry a source locator:

~~~text
source passage / equation / figure / dataset field / protocol step:
analyst inference, if any:
~~~

If no source locator is available, label the relation:

~~~text
ANALYST_INFERENCE / NOT SOURCE-ESTABLISHED
~~~

Neutral paraphrase does not turn an analyst inference into a source-native relation.

Deletion test:

~~~text
remove proprietary GRG labels

if the substantive process / relation account collapses:
  PROJECTION RISK = HIGH
  STOP positive grammar claim
~~~

GRG may still supply questions, but it has not yet shown an independently source-supported relation.

## 3. Gate C — lens declaration

Every discovery case must state:

~~~text
which current GRG distinctions motivated the recut?
which source distinctions were recovered independently?
which relation was visible before GRG relabeling?
what alternative recut would challenge the GRG reading?
~~~

This prevents a GRG lens from masquerading as neutral decomposition.

## 4. Gate D — no mandatory object inventory

The following are never mandatory source objects merely because GRG uses them:

~~~text
reach
support
proxy
friction
Generative Order
locus
reconstructibility
Selection
retention
~~~

Allowed result:

~~~text
object correspondence:
  NONE

grammar / reconstruction value:
  OPEN / POSITIVE / NEGATIVE
~~~

No penalty for zero correspondence.

## 5. Gate E — nontriviality

Reject as grammar gain when the candidate is only:

- state -> transition -> state;
- generic feedback;
- "history matters";
- "context matters";
- persistence;
- adaptation;
- "some constraints change later constraints";
- unrestricted "relations generate relations";
- restatement of the source equation in GRG prose.

A candidate must retain at least one nontrivial:

- admission condition;
- exclusion;
- asymmetry;
- intervention sensitivity;
- boundary condition;
- negative case;
- failure condition;
- re-objectification invariant.

## 6. Gate F — discovery / test mode declaration

Every case must declare one:

~~~text
mode = DISCOVERY
or
mode = TEST
~~~

### DISCOVERY

No M3/M4 claim from the same case that generated the candidate.

### TEST

Require pre-freeze of:

- relation burden;
- scope;
- legitimate redescription / re-objectification family;
- negative case;
- failure condition;
- comparator / mature baseline.

If these were chosen after decisive target inspection:

~~~text
independent recurrence = NOT PAID
~~~

## 7. Gate G — freeze relations, not vocabulary

A pre-freeze must be expressible without requiring source adoption of a GRG name.

Bad:

> "Find the GRG support object in the target domain."

Pedagogical form only — **not a frozen grammar claim and not M3 evidence**:

> "If a predeclared dependency D is claimed to maintain an operational equivalence between configurations A and B, then perturbing D should produce a predeclared divergence between A and B; a matched perturbation that leaves D intact is a negative case."

The point is syntactic: freeze a relation, comparator and failure boundary without requiring a source object to carry a GRG name.

Do not treat this example itself as an admitted GRG candidate. Any real candidate still requires source-native grounding, pre-freeze and absorption review.

## 8. Gate H — re-objectification stress

When a claim is supposed to be cross-objectification:

1. name at least one legitimate alternative cut where available;
2. state what must remain invariant;
3. state what is allowed to change;
4. state what result would count as failure.

Do not demand invariance where the source itself says the phenomenon is representation-relative.

Possible result:

~~~text
relation survives:
  YES / PARTIAL / NO / NOT TESTABLE

causal-level attribution survives:
  YES / PARTIAL / NO / N.A.
~~~

## 9. Gate I — absorption

Before prospective gain, run **both** source-native absorption and existing-GRG-owner semantic absorption.

Existing-GRG-owner check:

> Is the proposed burden already owned, decomposed, or typed by GRG v0.3, the 2026-09-22 capacity / intervention / reach / reconstructibility records, GTS composition, or an active canonical SRT owner?

If yes, prefer `INHERIT / DECOMPOSITION / CALIBRATION / OPERATIONALIZATION / SOURCE_REALIZATION` over a new GRG name.

Before prospective gain against the mature source:

> Does mature source-native practice already own the same useful relation, variable distinction, diagnostic, control or intervention question?

If yes:

~~~text
source reconstruction:
  may be valid

GRG prospective gain:
  ABSORBED / NO
~~~

Do not rescue the gain by renaming the source-owned result more abstractly.

## 10. Gate J — failure rights

A test-mode candidate must be able to end in:

~~~text
REJECTED
NARROWED
DOMAIN-LIMITED
ABSORBED
TYPE-MISMATCH
INSUFFICIENT-EVIDENCE
~~~

Not every failure should trigger a new abstraction.

If a candidate is revised:

~~~text
old candidate verdict remains
new candidate receives a new version / freeze

if target T caused / informed the failure or revision:
  T is contaminated for the revised candidate
  T != held-out evidence for the revised candidate
~~~

## 11. Gate K — GRG self-revision evidence

A discovery programme where every source changes only the source-side mapping and never pressures GRG is suspicious.

Review question:

> What in this case could make GRG's current objectification worse, unnecessary or differently cut?

Valid answers include:

- delete a field;
- split a relation;
- merge two GRG constructs;
- change unit / grain;
- reject a formalism;
- keep source vocabulary instead;
- conclude no reusable grammar candidate.

## 12. Gate L — formalization drift

When equations are introduced, ask:

~~~text
is this symbol a GRG working coordinate
or
a claimed source-native variable identity?
~~~

If identity is claimed, require source evidence.

Do not infer:

~~~text
same algebraic role
= same mechanism
= same ontology
~~~

A formal correspondence can be useful without ontological identity.

## 13. Gate M — Card placement

Fusion-Case Card fields must not be populated as the first analytic move.

Required ordering:

~~~text
source-native account
-> reconstruction record
-> relation / missing-relation result
-> candidate status
-> only then Card mapping / non-identity audit
~~~

If the Card is driving source extraction:

~~~text
STOP
return to source-native reconstruction
~~~

## 14. Gate N — grammar gain / payoff

Before positive payoff, answer all relevant questions:

1. What became more coherent than the source models considered separately?
2. What missing relation / hidden dependency was exposed?
3. What source objectification was shown to combine distinct roles, if any?
4. What new diagnostic / failure / intervention question follows?
5. What mature source theory already owns this result?
6. What would make the grammar candidate fail?

If none of 1–4 is paid:

~~~text
REDESCRIPTIVE_ONLY
~~~

If 5 absorbs the result:

~~~text
GRG INCREMENTAL GAIN = NO
~~~

## 15. Review checklist

A reviewer should be able to answer:

~~~text
[ ] source-native first was actually executed
[ ] relevant GRG cuts were also treated as explananda
[ ] existing GRG-owner semantic absorption was checked before new naming
[ ] GRG vocabulary did not determine the source object inventory
[ ] zero object correspondence was allowed
[ ] GRG lens / projection risk was declared
[ ] discovery vs test mode was explicit
[ ] test-mode relation was frozen before decisive held-out inspection
[ ] no target used to diagnose / revise the candidate is reused as held-out confirmation
[ ] legitimate re-objectification stress was considered where applicable
[ ] trivial state-transition / feedback restatement was excluded
[ ] mature-neighbor absorption was checked for positive gain
[ ] failure conditions can reject the candidate
[ ] revision would not retroactively erase a failed version
[ ] Card mapping happened after generative reconstruction
[ ] M0–M5 and XG burdens were not bypassed
~~~

## 16. Stop rules

STOP positive grammar progression when any applies:

- source-native account is not yet adequate;
- the only evidence is vocabulary resemblance;
- the candidate was generated and "independently confirmed" in the same inspected case;
- the relation cannot be stated without GRG labels;
- no negative / failure case can be named;
- a generic dynamics template does all the work;
- mature source practice already owns the claimed incremental distinction and no separate replication rationale exists;
- repeated cases only add more mappings but no stronger grammar burden;
- a failed candidate is being silently rewritten and counted as if it had passed.
