# GRG X4c Inheritance Carrier Role Library v0.1

## 0. Role

This library records only carrier roles that earned reusable status through bounded census.

It is not:

- a new ontology;
- a complete taxonomy of inheritance;
- a mechanism library for mature domains;
- an M-status ladder;
- a claim that all X4c realizations must use these roles.

Owner audit:

Operations/Audits/SRT_GRG_INHERITANCE_CARRIER_ROLE_CENSUS_PASS1_2026-09-21.md

## 1. Admission rule

A reusable role enters by one of two routes.

### CORE / recurrence route

~~~text
>= 2 paid independent source-native carrier records
+
clear non-identity from adjacent roles
+
predicts a useful exclusion / near-control / failure condition.
~~~

### SPECIALIZED / discrimination route

~~~text
1 strong paid source-native record
+
role is necessary for a contrast adjacent roles cannot explain
+
strong near-control isolates the role.
~~~

A specialized role is reusable as a discriminating question.

It is not claimed broadly recurrent.

## 2. Current library

| Role | Library status | Paid basis | Main question |
|---|---|---|---|
| SUBSTRATE | CORE | ecological inheritance; CIV-006; IPv4/IPv6 | what preserves enough of F for successors to encounter it? |
| PAYLOAD | CORE | IPv4/IPv6; precedent | what structured inherited content must remain this content rather than another? |
| INTERFACE | CORE | CIV-006; IPv4/IPv6 | how are successor access / compatibility / transition possibilities conditioned? |
| AUTHORITY | SPECIALIZED | precedent / stare decisis | what changes binding / mandatory / admissible force without merely changing content availability? |

## 3. SUBSTRATE — CORE

Definition:

~~~text
SUBSTRATE
= a carrier component that preserves enough of reconstructed field F
  for the successor cohort / cycle to encounter that field.
~~~

Current paid realizations:

- ecological modified environment;
- maintained sewer network;
- installed technical infrastructure / hosts / routers / applications.

Non-identities:

~~~text
SUBSTRATE != PAYLOAD

the medium that preserves F
is not identical to
the structured content carried by F.
~~~

~~~text
SUBSTRATE != INTERFACE

persistence of F
does not itself specify
how the successor process couples to F.
~~~

Predicted failure condition:

~~~text
if the claimed substrate no longer preserves enough of F
into the successor cohort,
the SUBSTRATE role fails
and X4c may fail.
~~~

Control pressure:

- remove / lose the persistent carrier while holding prior reconstruction history fixed;
- compare preserved versus non-preserved reconstructed condition where source-native evidence permits.

## 4. PAYLOAD — CORE

Definition:

~~~text
PAYLOAD
= structured inherited content whose identity matters
  to the successor field.
~~~

Current paid realizations:

- IPv4 protocol / address semantics;
- precedential holding / legal-rule content.

Non-identities:

~~~text
PAYLOAD != SUBSTRATE

the same substrate may carry different content.
~~~

~~~text
PAYLOAD != AUTHORITY

availability of content
does not establish binding force.
~~~

Predicted failure condition:

~~~text
if changing / removing inherited content
does not alter the successor field
while relevant carrier context is preserved,
PAYLOAD is not paid.
~~~

Control pressure:

- content present versus absent / changed;
- same or similar content under different authority relation where source-native comparison permits.

## 5. INTERFACE — CORE

Definition:

~~~text
INTERFACE
= a carrier role that materially conditions
  how successor processes access, interoperate with,
  work through, bypass or replace inherited field F.
~~~

Current paid realizations:

- combined-sewer network as hydraulic / retrofit constraint;
- IPv4 installed base as compatibility / migration constraint.

Non-identities:

~~~text
INTERFACE != SUBSTRATE

F can persist
without the claimed successor coupling pathway being established.
~~~

~~~text
INTERFACE != PAYLOAD

access / compatibility can change
without changing inherited symbolic content.
~~~

Strong current near-control:

~~~text
existing installed base
vs
greenfield
~~~

Generalized failure condition:

~~~text
if removing / bypassing the proposed interface component
does not change successor access / compatibility /
transition possibilities,
INTERFACE is not paid.
~~~

## 6. AUTHORITY — SPECIALIZED

Definition:

~~~text
AUTHORITY
= a carrier role that changes binding / mandatory /
  admissible force without merely changing
  informational availability.
~~~

Current paid realization:

- precedent / stare decisis.

Strong near-controls:

~~~text
binding precedent
vs
persuasive authority
~~~

and:

~~~text
controlling precedent
vs
case of first impression
~~~

Non-identities:

~~~text
AUTHORITY != PAYLOAD

the same / similar reasoning may remain available
while binding force differs.
~~~

~~~text
AUTHORITY != INTERFACE

mandatory force is not merely technical access / compatibility.
~~~

Current library status:

~~~text
SPECIALIZED
broad cross-domain recurrence = OPEN
~~~

Do not promote AUTHORITY to CORE without a second independently grounded realization.

## 7. Roles not admitted to v0.1

### ENACTMENT — CASE-LOCAL / NARROW

Reason:

- only one current carrier record;
- not independently isolated from INTERFACE / implementation;
- risks duplicating X3b operative-expectation burden.

It may be used locally where a source requires the word.

It is not a reusable Role Library entry.

### REPRODUCTION — OPEN / NOT PAID

No current worked X4c carrier independently isolates it as a reusable component role.

Do not infer it from the word "generation" or from ecological inheritance in general.

### MAINTENANCE — RETYPED

Not a reusable component role in v0.1.

Move to architecture-level persistence process.

## 8. Persistence process — separate from component role

Carrier architecture should separately record:

~~~text
persistence process =
PASSIVE-PERSISTENCE
ACTIVE-MAINTENANCE
RECURRENT-REPRODUCTION
MIXED
OPEN
~~~

This asks:

> how does the carrier architecture continue to be available across the successor boundary?

It does not ask:

> what causal role does a carrier component play for the successor?

Examples:

~~~text
ecological modified environment:
persistence process = PASSIVE-PERSISTENCE / source-bounded

CIV-006 sewer:
persistence process = ACTIVE-MAINTENANCE / MIXED over long horizon

IPv4/IPv6 installed base:
persistence process = MIXED / implementation and installed-base continuity

precedent:
persistence process = institutional reproduction / continuing adjudicative practice
but exact process typing remains source-local.
~~~

Do not promote a persistence-process value into a carrier role automatically.

## 9. Admission-order guard

Negative-productivity owner:

Operations/Audits/SRT_GRG_CIV005_CARRIER_ROLE_LIBRARY_NEGATIVE_PASS1_2026-09-21.md

A reusable role must not bootstrap X4c relation admission.

Forbidden loop:

~~~text
persistent environment
-> label SUBSTRATE
-> carrier role exists
-> therefore inheritance exists.
~~~

Before relation-level successor / transmission burdens are paid, use:

~~~text
ROLE-CANDIDATE / PRE-ADMISSION
= source-native component plausibly fits a reusable role,
  but X4c successor-boundary / field-transmission admission
  is not yet established.
~~~

This status:

- may guide evidence search;
- may identify the likely carrier component;
- cannot count toward architecture sufficiency;
- cannot strengthen X4c maturity;
- cannot be promoted to COMPONENT-ROLE-PASS by analogy from another source family.

Admission order:

~~~text
candidate reconstructed field F
-> declared successor cohort / cycle
-> F transmitted / preserved across that boundary
-> successor enters under F
-> successor possibilities materially changed by F
-> COMPONENT-ROLE-PASS inside admitted carrier architecture
~~~

## 9.2 Use rule

For an X4c carrier architecture:

1. identify the source-native component;
2. state provenance metadata;
3. declare the successor boundary before awarding a paid carrier role;
4. use ROLE-CANDIDATE / PRE-ADMISSION where relation admission is still open;
5. assign only paid reusable roles after successor / transmission burden is met;
6. leave unsupported proposed roles ROLE-OPEN;
7. record source-local roles separately if needed;
8. record architecture persistence process separately;
9. specify a near-control / failure condition for each reusable role where possible;
10. state the minimal paid role set sufficient for the declared X4c mapping.

## 10. Anti-inflation rule

Do not force every architecture to instantiate every library role.

~~~text
role absent
!= defect

role count
!= maturity

more roles
!= stronger X4c
~~~

The minimum sufficient architecture is preferred.

## 11. Relation / expectation / PH boundary

~~~text
carrier role
!= X4c relation identity
!= expectation provenance
!= PH position/horizon consequence
!= moral legitimacy
~~~

Examples:

- AUTHORITY role does not make an institution legitimate;
- PAYLOAD does not make content true;
- SUBSTRATE persistence does not make a relation good;
- INTERFACE constraint does not imply unjust lock-in.
