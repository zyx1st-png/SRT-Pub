# GRG Fusion-Case Card Iteration Plan — 2026-09-23

## 0. Scope

This plan records the next bounded route after the FRR-driven Card v0.2 refinement.

It does not authorize:

- GRG v0.4;
- broad canonical GRG expansion;
- BCTB T2;
- a universal-grammar claim;
- a new deep-well programme that bypasses current repository governance.

The working object is the **experimental Grammar Card**, not canonical SRT.

## 1. Framing correction

Future cases should not be called “enemy cases”, “hostile cases” or adversarial cases by default.

Use:

> **fusion case**

A fusion case has two simultaneous duties:

1. preserve the source-native mechanism and vocabulary well enough that GRG cannot win by relabeling;
2. allow the source to modify, split, demote or reject parts of the Card / GRG mapping.

The intended direction is reciprocal:

`source -> GRG pressure`

and

`GRG -> new questions / explicit comparison burdens for source reconstruction`.

A good fusion case can end with:

- successful partial instantiation;
- type mismatch;
- mapping rejection;
- Card field split;
- Card field deletion;
- a new OPEN problem;
- no GRG gain.

All are valid outcomes.

## 2. Core iteration loop

For each case:

`source-native reconstruction`

`-> bounded Card fill`

`-> explicit non-identity guard`

`-> anti-metaphor test`

`-> generative expectation / failure condition`

`-> outcome`

`-> Card revision candidate`

`-> cross-card reconciliation`.

Do not start by searching for GRG vocabulary inside the source.

Do not require all twenty Card blocks to be filled.

Stop where source support stops.

## 3. Fusion Case 1 — FRR

Status:

- source-grounded focused reading exists;
- Card v0.2 derivation exists in this package;
- FRR should remain the first provenance case, not the universal template owner.

Current main lessons:

- source-native “selection” must be separated from SRT Selection;
- actuality criterion != occurrence explanation;
- structural reopening != GRG reconstructibility;
- non-identity guards are mandatory;
- pre-Selection organization deserves its own Card region;
- source-native and GRG provenance must remain reconstructible.

## 4. Fusion Case 2 — evolutionary biology / population genetics

Recommended next domain because it contains source-native mechanisms that place useful pressure on Card distinctions without being structurally identical to FRR.

First-pass questions:

- biological natural selection != SRT Selection: what is the exact type relation?
- mutation: difference production vs Selection occurrence;
- drift: actual differentiation without adaptive direction;
- allele-frequency change: event individuation and scale dependence;
- recessive / currently silent variation: difference existence vs current reach;
- fixation / extinction: occurrence vs retention vs terminality;
- fitness landscape: does “Selection-burden landscape” do analytical work or become metaphor?
- niche construction: does retained organization recondition later generative conditions?
- evolutionary transitions in individuality: only after the basic Card pass, test higher-order formation.

Method guard:

Do not force population genetics into SRT vocabulary.

Use mature source-native evolutionary terminology first.

## 5. First cross-card reconciliation — FRR × evolution

Do this before opening a third major fusion case.

Questions:

- Which Card fields genuinely carry the same generative role?
- Which FRR-driven fields are absent or awkward in evolution?
- Which fields are overfit to quantum / process-philosophy vocabulary?
- Which evolution-side distinctions force new field splits?
- Does the Selection audit survive both cases?
- Does the proxy / neutrality block remain useful without becoming universal metaphor?
- Is the reconstructibility split still needed in both?
- Which mappings are analogies only?
- Can either case generate a nontrivial expectation for the other without ad hoc retuning?

Expected output:

`Grammar Card v0.3 candidate`

only if the case comparison actually warrants a template revision.

This does **not** mean GRG foundational owner v0.4.

## 6. Fusion Case 3 — distributed systems / network protocols

Recommended after the first cross-card reconciliation because the domain has hard source-native structures:

- state;
- messages;
- routing;
- permissions;
- consensus;
- partitions;
- retries;
- failover;
- reconfiguration;
- protocol versions.

This domain can test whether GRG fields remain precise when the mechanisms are engineered, explicit and operational.

Useful pressures:

- source-native event individuation;
- reach as routing / admissibility;
- proxy vs protocol state;
- equivalence classes;
- retained configuration;
- structural reopening / reconfiguration;
- higher-order control-plane formation;
- intervention-sensitive expectations.

The goal is not to claim distributed systems instantiate SRT ontology wholesale.

## 7. Later fusion domains

Only after the Card survives several heterogeneous cases should later work expand toward:

- money / credit / institutions;
- cognition / neuroscience;
- AI architectures;
- social coordination;
- language / representation.

These domains are especially vulnerable to premature import of GRG notions such as bearer, endogenous perspective, stake, normativity and agency.

The downstream research package from the same dialogue should be used as a hypothesis reservoir, not as a required Card vocabulary.

## 8. Cross-case admission discipline

A GRG concept should gain stronger standing only when:

- it is reconstructible in source-native terms across multiple cases;
- it does not erase important source distinctions;
- it changes a diagnostic / expectation / intervention / failure boundary;
- it survives explicit non-identity audit;
- contrary cases are preserved rather than explained away;
- the mapping can be reopened.

Do not count repeated vocabulary matches as evidence.

## 9. Card-change log requirement

Every fusion case should end with:

```text
Card fields retained:
Card fields revised:
Card fields split:
Card fields removed:
Card fields left empty:
new source-native distinctions:
failed GRG mappings:
new non-identity guards:
new generative expectations:
new failure / recut conditions:
next cross-card question:
```

This change log is more important than a case “score”.

## 10. Repository writeback pattern

Preferred artifacts for each case:

1. source-grounded reading / reconstruction note;
2. filled experimental Grammar Card;
3. case-specific mapping / non-identity audit;
4. Card-change log;
5. only when warranted, cross-card reconciliation proposal.

Do not update the foundational GRG owner automatically after each case.

Accumulate enough case pressure first.
