# GRG Fusion-Case Card Iteration Plan — 2026-09-23

## 0. Scope

This plan records an author-requested bounded **companion route** after the FRR-driven Fusion-Case Card v0.1 refinement.

It does **not** silently replace the current STATUS route. At PR creation, live STATUS still records:

`CURRENT NEXT = bounded latent-reconstructive-reach reality pressure-test / operationalization`.

Until STATUS is explicitly reconciled, a fusion case may proceed only if it is scoped to serve that current bounded pressure-test / operationalization, or after that routed work is separately closed / re-routed. The plan itself is not a STATUS owner.

It does not authorize:

- GRG v0.4;
- broad canonical GRG expansion;
- BCTB T2;
- a universal-grammar claim;
- a new deep-well programme that bypasses current repository governance.

The working object is the **experimental Fusion-Case Card companion overlay**, not canonical SRT. The active GTS v0.2 remains the primary process-first GRG record and the live M0–M5 / M4-E0 machinery remains authoritative for maturity and prospective transfer claims.

## 0.1 Cross-objectification method correction — 2026-09-23

The fusion lane must not use object-to-object mapping as its research engine.

Companion method:

- `Operations/Proposals/SRT_GRG_CROSS_OBJECTIFICATION_GENERATIVE_ARCHITECTURE_V0_1_2026-09-23.md`;
- `Operations/GRG/SRT_GRG_CROSS_OBJECTIFICATION_ANTI_DRIFT_PROTOCOL_V0_1_2026-09-23.md`;
- `Operations/Templates/SRT_GRG_CROSS_OBJECTIFICATION_RECONSTRUCTION_RECORD_V0_1_2026-09-23.md`.

Hard correction:

~~~text
domain object
-> GRG object
-> correspondence score
~~~

is not a valid primary fusion-case sequence.

Use instead:

~~~text
source-native reconstruction
-> objectification declaration / legitimate recut
-> domain-native generative reconstruction
-> coherence / missing-relation search
-> grammar candidate extraction
-> test-mode freeze if a cross-objectification claim is promoted
-> GTS / XG / M-level test where warranted
-> Fusion-Case Card as late mapping / non-identity / schema audit
~~~

The Card remains useful, but it is no longer allowed to drive source extraction.

A case with zero natural GRG-object correspondence may still be useful. Conversely, a large number of apparent correspondences does not establish grammar gain.

This correction does not change the live STATUS current-next and does not activate a third fusion case.

## 1. Framing correction

Future cases should not be called “enemy cases”, “hostile cases” or adversarial cases by default.

Use:

> **fusion case**

A fusion case has two simultaneous duties:

1. preserve the source-native mechanism and vocabulary well enough that GRG cannot win by relabeling;
2. allow the source to modify, split, demote or reject parts of the Card / GRG mapping.

The intended direction is reciprocal:

`source -> GRG pressure`

and

`GRG -> new questions / explicit comparison burdens for source reconstruction`.

A good fusion case can end with:

- successful partial instantiation;
- type mismatch;
- mapping rejection;
- Card field split;
- Card field deletion;
- a new OPEN problem;
- no GRG gain.

All are valid outcomes.

## 2. Core iteration loop

For each case, first declare:

~~~text
mode = DISCOVERY / TEST
~~~

Then use:

`source-native reconstruction`

`-> Cross-Objectification Reconstruction Record`

`-> objectification / recut audit`

`-> domain-native generative reconstruction`

`-> coherence + missing-relation search`

`-> candidate grammar extraction, if warranted`

`-> TEST freeze before held-out inspection, if promoting a recurrence / gain claim`

`-> GTS / XG / M-level route where warranted`

`-> Fusion-Case Card late audit`

`-> explicit non-identity + anti-metaphor / absorption test`

`-> outcome + GRG self-revision`

`-> cross-case reconciliation`.

Do not start by searching for GRG vocabulary inside the source.

Do not use mapping density as a score.

Do not count a DISCOVERY-generated candidate as independently confirmed by the same case.

Do not require all Card blocks to be filled.

Stop where source support stops.

## 4. Fusion Case 2 — evolutionary biology / population genetics

Recommended **only after reconciling the live STATUS current-next route** because it contains source-native mechanisms that may place useful pressure on Card distinctions without being structurally identical to FRR.

The items below are reading guides, not precommitted GRG mappings. Begin from mature evolutionary / population-genetic source-native accounts and allow the source to reject the listed framing.

First-pass generative-reconstruction questions:

- how are heritable differences generated, maintained and exposed?
- which developmental, genetic, ecological and population conditions change whether a difference becomes consequence-bearing?
- how do selection, drift, reproduction, demography and mutation jointly constrain realized population transitions without preassigning them GRG/SRT object identities?
- how do realized outcomes alter later genetic / ecological / population conditions?
- where do population genetics, developmental robustness / canalization, evolvability / CGV and niche-construction accounts hand off to one another?
- do those interfaces contain a missing or overloaded generative relation that mature source practice has not already integrated?
- which source objectifications remain stable under alternative causal / statistical / level decompositions?
- only after the basic reconstruction should higher-order formation or transitions in individuality be considered.

Late audit questions may still ask whether current GRG terms are useful, but only after the generative reconstruction exists.

Method guard:

Do not force population genetics into SRT or GRG vocabulary.

Do not treat natural selection, drift, fixation, fitness, CGV or niche construction as objects waiting for a GRG counterpart.

Use mature source-native evolutionary terminology first.

## 5. First cross-case reconciliation — FRR × evolution

Do this before opening a third major fusion case.

Start from the two **reconstruction records**, not from Card field alignment.

Questions:

- What domain-native generative relations were reconstructed in each case?
- What became more coherent inside each source domain, if anything?
- What missing / overloaded / hidden relation was exposed in either case?
- Which candidate relations survive legitimate re-objectification, and which are case-local?
- Which source mechanisms differ while still paying a genuinely shared burden?
- Which candidate was generated only after seeing the case and therefore remains DISCOVERY-only?
- Which mature source theory already absorbs a proposed gain?
- What did each case force GRG itself to split, delete, merge or leave source-native?
- Only after those questions: which late Card fields remain useful as audit / non-identity surfaces?

Possible outputs:

- revised reconstruction method;
- a DISCOVERY-level grammar candidate;
- Card field split / removal / demotion;
- no reusable grammar candidate;
- `Fusion-Case Card v0.2 candidate` only if late-audit schema revision is actually warranted.

This does **not** mean GTS v0.2 is replaced, does **not** establish M3/M4, and does **not** mean GRG foundational owner v0.4.

## 6. Fusion Case 3 — distributed systems / network protocols

Recommended after the first cross-card reconciliation because the domain has hard source-native structures:

- state;
- messages;
- routing;
- permissions;
- consensus;
- partitions;
- retries;
- failover;
- reconfiguration;
- protocol versions.

This domain can test whether GRG fields remain precise when the mechanisms are engineered, explicit and operational.

Useful reconstruction pressures:

- how source-native event / transition units are individuated;
- how routing, permission, membership and admissibility are actually represented and enforced;
- how protocol state, control-plane state and derived representations differ in role;
- how equivalence classes or compatibility rules are constituted source-natively;
- how configuration persists, is replaced, or becomes operative in later transitions;
- how reconfiguration changes later reachable / permitted transitions;
- how control-plane organization changes lower-level transition conditions;
- which of these dependencies survive alternative legitimate protocol / state decompositions.

These are source-native reconstruction prompts, not names of GRG objects to locate.

The goal is not to claim distributed systems instantiate SRT ontology wholesale.

## 7. Later fusion domains

Only after the Card survives several heterogeneous cases should later work expand toward:

- money / credit / institutions;
- cognition / neuroscience;
- AI architectures;
- social coordination;
- language / representation.

These domains are especially vulnerable to premature import of GRG notions such as bearer, endogenous perspective, stake, normativity and agency.

The downstream research package from the same dialogue should be used as a hypothesis reservoir, not as a required Card vocabulary.

## 8. Cross-case admission discipline

A grammar candidate / GRG working distinction should gain stronger standing only when:

- it is reconstructible in source-native terms across multiple cases;
- it does not erase important source distinctions;
- the strongest reasonable horizontal / source-native baseline is declared;
- mature-neighbor ownership is paid when stronger comparison / prospective credit is claimed;
- it changes a diagnostic / expectation / intervention / failure boundary;
- it survives explicit non-identity audit;
- contrary cases are preserved rather than explained away;
- the mapping can be reopened;
- live M0–M5 maturity is recorded separately from Card-local correspondence.

For any prospective M4-side transfer claim, freeze the target/design before decisive target-source or outcome inspection and apply M4-E0. If ordinary target-domain practice already owns the distinction/control, record `M4 = NO / ABSORBED` and stop duplicate execution.

Do not count repeated vocabulary matches as evidence.

### 8.1 Stop-loss / contraction rule

The fusion-case programme must be able to shrink as well as grow.

**Adequacy must be declared before interpreting the case outcome.** A case counts as source-native adequate for this rule only when, before its GRG result is scored:

- source identity / reading boundary and source anchors are explicit;
- the source-native event / process unit (§2) is at least sufficiently specified to audit the declared grain;
- the strongest reasonable source-native / horizontal baseline required by the live research framework is named;
- missing later Card fields are allowed and do not retroactively make the case "inadequate".

A Card revision counts as **reusable** for stop-loss purposes only after it survives the next heterogeneous cross-card reconciliation; a case-local wording change alone does not exempt the programme from contraction.

Mandatory root-return:

- if **two consecutive source-native adequate fusion cases** produce no grammar candidate stronger than M0/M1, no new falsifiable burden, and no reconstruction / Card revision that survives heterogeneous cross-case reconciliation, **pause acquisition of new domains** and perform grammar / Card contraction plus root-question review before opening another case;
- if the same mandatory Card field is `N.A.`, `TYPE_MISMATCH` or `INSUFFICIENT_EVIDENCE` in two heterogeneous adequate cases, mark that field as a split/removal candidate at the next cross-card reconciliation;
- a third case may not be opened merely to rescue a favored field or GRG term after the stop condition fires.

Valid stop outcomes include: simplify the Card, demote a GRG term, return the burden to GTS/source-native records, or park the fusion lane.

## 9. Card-change log requirement

Every fusion case should end with:

```text

Card fields revised:
Card fields split:
Card fields removed:
Card fields left empty:
new source-native distinctions:
failed GRG mappings:
new non-identity guards:
new generative expectations:
new failure / recut conditions:
next cross-card question:
```

This change log is more important than a case “score”.

## 10. Repository writeback pattern

Preferred artifacts for each case:

1. source-grounded reading / reconstruction note;
2. **Cross-Objectification Reconstruction Record**;
3. if a bounded transformation is stable enough, GTS record / pointer;
4. only after reconstruction, optional filled Fusion-Case Grammar Card as late mapping / non-identity audit;
5. GRG self-revision + Card-change log where relevant;
6. only when warranted, cross-case reconciliation proposal.

A Card is not required merely to make a case count as source-native adequate.

Do not update the foundational GRG owner automatically after each case.

Accumulate enough case pressure first.
