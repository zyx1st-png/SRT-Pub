# SRT Constitution + Domain Architecture v2

## Add the Domain Reconstruction Layer between Constitution and deep wells

> **Author decision, 2026-09-04.** Constitution v1 is complete, but the programme should not jump directly from constitutional reader-operations to traditional domain theories, datasets and experiments. Each selected domain first requires a domain-level reconstruction surface derived from the Constitution, the domain's own starting objects, the repository's inherited domain assets, and the full relevant material record.

This is an architecture correction, not a new constitutional layer and not a return to domain axiom towers.

---

## 0. The repaired architecture

The active programme architecture is now:

```text
LAYER 1 — SRT Constitution
cross-domain reader operations / explanatory burdens
no domain mechanism or empirical result asserted here

        ↓

LAYER 2 — Domain Reconstruction Framework
Constitution × domain starting picture × inherited SRT assets × materials
reconstructs the domain's problem-space, objectification map,
bearer/position architecture and research families

        ↓

LAYER 3 — Domain Theory / Hypothesis / Model
specific mechanisms, formalizations, proxies and candidate explanations

        ↓

LAYER 4 — Deep Wells / Evidence
bounded questions, strongest-baseline comparison,
experiments / data / archives / historical tests / Case A-B-C gates

        ↓

LAYER 5 — Productive writeback and eventual cross-domain synthesis
framework writeback occurs after each completed or legitimately blocked deep well;
cross-domain synthesis does not begin until at least two deep wells have independently produced usable results
```

The key correction is the insertion of **Layer 2**.

Old shortcut:

```text
Constitution
-> deep-well charter
-> data / literature / experiment
```

New route:

```text
Constitution
-> Domain Reconstruction Framework
-> specific domain hypothesis / deep-well selection
-> evidence
-> framework writeback
```

---

## 1. What a Domain Reconstruction Framework is

A Domain Reconstruction Framework is a **domain-level SRT problem map**.

It answers:

> If Constitution v1 is brought into this domain before any one experiment, dataset or favorite theory is selected, how does the domain's problem-space get reorganized?

It is not:

- a second Constitution;
- a domain axiom system;
- a claim that Constitution deductively derives the domain;
- a literature review;
- a deep-well protocol;
- a substitute for the field's strongest existing theories;
- a place to promote old SRT formalisms by default.

The preferred role is:

```text
Constitution supplies executable perspective operations
+
domain supplies its actual objects, methods and constraints
+
repository/material history supplies inherited evidence, hypotheses and failures

->

Domain Reconstruction Framework organizes the resulting question-space
```

---

## 2. Mandatory sections of every Domain Reconstruction Framework

Each active framework should contain at least the following.

### 2.1 Domain starting picture / Given-Ones inventory

Recover what the field ordinarily treats as salient public objects, units, states, agents, methods, systems or outcomes.

The inventory is descriptive, not accusatory. A Given One is not presumed wrong merely because it is given.

### 2.2 Constitution-to-domain translation

Run all six Constitution reader operations in domain-native language:

```text
ARTICULATION
STILL-THIS
OWN-HISTORY
CURRENT PROCESSABILITY
CONSEQUENCE ATTRIBUTION
EVALUATIVE RE-RUN
```

For each operation record:

```text
domain question opened
what existing object/unit it pressures
what it does NOT yet claim
```

### 2.3 Domain objectification map

Record the major practices that make the domain's public objects portable and comparable, for example:

```text
boundary selection
grain / timescale
normalization
canonical representation
trial or case equivalence
aggregation / averaging
archive inclusion
periodization
model-state construction
proxy choice
subject or unit pooling
```

For each, ask what is preserved, what is intentionally discarded, and what loss could matter to an SRT-sensitive question.

### 2.4 Bearer / position architecture

Separate candidate roles rather than collapsing them:

```text
measurement object
causal unit
historical bearer
behavioral bearer
consequence bearer
phenomenal bearer
analyst / observer position
community / institutional participant
```

No stronger bearer, subjecthood or phenomenality claim follows merely from listing these roles.

### 2.5 Domain problem families

The framework should group the reconstructed question-space into a small number of stable problem families.

A problem family is broader than one experiment but narrower than the Constitution.

Example shape:

```text
N1 state identity
N2 history ownership
N3 relational disposition
N4 bearer hierarchy / consequence landing
N5 measurement objectification
N6 pathology / evaluative basis
```

Identifiers are domain-local organizational labels, not new canonical symbols.

### 2.6 Existing SRT asset re-routing

Read the repository's inherited domain files before drafting a new framework.

Classify existing assets as appropriate among:

```text
domain-framework precursor
historical domain theory
candidate mechanism
formal model
operational proxy
evidence packet
experiment / protocol
claim-status guardrail
patch / material bridge
legacy / superseded expression
unresolved tension
```

The framework may reuse them, but old files do not define the new framework merely because they already exist.

### 2.7 Traditional domain neighbors

At framework level, identify the main mature traditions adjacent to each problem family.

Purpose:

- terminology competence;
- known objections;
- locating where later strongest-baseline audits must look.

Do not run a novelty permission gate here. Full Case A/B/C adjudication belongs to the selected deep well.

### 2.8 Deep-well queue

Only after sections 2.1-2.7 should the framework propose candidate deep wells.

A deep well should name:

```text
parent problem family
exact bounded question
why domain-native evidence can discriminate it
strong-rival availability
scope / access constraints
```

## 3. Mandatory Pre-framework Material Re-entry Pass

This pass addresses a repository failure mode exposed by the reconstruction: valuable source material can remain stranded as SourceCards, patches, hooks, old domain files or evidence packets without materially shaping the domain framework.

No active Domain Reconstruction Framework may be drafted from Constitution + a few recent papers alone.

### 3.1 Required input surfaces

Before Framework v0.1, retrieve and route at minimum the relevant items from:

```text
01_Source_Intuition/ and active book drafts
legacy / current domain owner files
claim-status and compact-core files
Materials/YYYY/ SourceCards
<Domain>/patches/
<Domain>/hooks/ and landing ledgers
Operations/_SRT_MATERIAL_LOG.md
relevant Material_Log monthly records
Operations/Context_Bundles for the domain
Experiments/ and domain evidence packets where relevant
OPEN_TENSIONS / audits that bear directly on the domain
published/submitted manuscript-local assets where historically relevant
```

This is a recovery-and-routing pass, not a mass rewrite.

### 3.2 Material Re-entry Matrix

The framework must maintain a bounded matrix or equivalent section containing, for each material that can materially affect the domain reconstruction:

| Field | Meaning |
|---|---|
| source / asset | SourceCard ID or repository path |
| source-native contribution | what the source / asset actually establishes |
| framework slot | Given One / objectification / bearer / problem family / neighbor / hypothesis / guardrail |
| role | evidence / mechanism / pressure / guardrail / historical precursor / candidate hypothesis |
| owner relation | already owned / partly owned / reverse constraint / unresolved overlap |
| disposition | integrated / routed-to-deep-well / deferred / excluded |
| reason | why this disposition is warranted |

`deferred` and `excluded` require reasons. Silence is not a disposition.

### 3.3 Completeness rule

The pass is not required to enumerate every low-value file in the repository.

It **is** required to account for:

- all domain-relevant `high` / `very_high` priority SourceCards that remain active;
- all active domain PatchNotes that claim a surviving bridge, pressure or mechanism;
- all active IntegrationHooks whose intended target falls inside the reconstructed domain;
- all inherited domain owner / claim-status files that a competent reader would reasonably expect to govern the topic;
- all current experiment/evidence assets directly related to the candidate problem families.

Each such item must end in one of:

```text
integrated into framework
routed to a specific problem family or deep well
deferred with named blocker
excluded with named reason
```

No material receives constitutional authority from being integrated.

### 3.4 Three-layer source discipline remains mandatory

Material integration preserves Pipeline 1's distinction:

```text
Layer A — source-derived claim
Layer B — SRT-side domain synthesis
Layer C — discriminating SRT claim, if any
```

The Domain Framework primarily lives at **Layer B**, constrained by Layer A.

Layer C still requires deep-well/rival evidence.

Therefore:

```text
source supports source claim
source may realize / constrain / pressure domain reconstruction
realization or resonance != proof of Constitution
```

### 3.5 No parallel material pipeline

This architecture does not replace `Operations/_SRT_MATERIAL_PIPELINE.md`.

Pipeline 1 remains the intake, source-fidelity and material-status owner.

The new pass answers a later question:

> Once a domain is selected for reconstruction, how do already processed materials become active inputs to that domain's problem architecture rather than remaining stranded repository objects?

## 4. Framework-before-deep-well gate

For all future domains:

```text
select domain
-> Pre-framework Material Re-entry Pass
-> Domain Reconstruction Framework v0.1
-> author review / scope lock
-> choose deep well from the framework queue
-> deep-well charter
```

A new deep-well charter should not carry the burden of constructing the entire domain worldview from scratch.

### Pilot/grandfather rule

Deep wells opened before this architecture correction remain valid pilot records.

They must not be erased or retrospectively presented as if a framework already existed.

Instead:

- Neuroscience first-well outputs become source material for a backfilled Neuroscience Reconstruction Framework;
- the current Epistemology deep-well work may retain its Phase-8A record, but further theory expansion should first identify its parent Epistemology Reconstruction Framework and problem family;
- adverse / translation-only / blocked results remain preserved when framework writeback occurs.

## 5. Distinguish Domain Framework from Domain Theory

This boundary is load-bearing.

Allowed in Domain Reconstruction Framework:

```text
which objects are being treated as one
which history / position / bearer distinctions are being erased or retained
which problem families become visible
which inherited assets map to which family
which mature traditions are relevant
which questions are worth a deep well
```

Not automatically allowed:

```text
specific causal mechanism is true
specific scalar/proxy is the correct domain realization
specific empirical prediction holds
specific formalism is privileged
SRT outperforms the field
```

Those belong to Layer 3 or Layer 4 and must pay their own evidence burden.

## 6. Phase 9.5 — Post-deep-well Domain Framework Writeback

A Domain Reconstruction Framework is **not frozen after v0.1**.

After every completed or legitimately blocked deep well, run a bounded writeback pass.

Input:

```text
deep-well result
strongest-baseline verdict
adverse / null / access-blocked results
new SourceCards / patches generated during the well
new objectification or bearer distinctions
newly exposed mature-domain ownership
```

For each parent problem family decide:

```text
retain
strengthen
narrow
split
merge
reclassify as translation-only
route to unresolved tension
withdraw
```

Writeback may change the domain framework.

It may **not** silently change Constitution v1.

If repeated domain writeback exposes a genuine constitutional defect, route it through the existing Constitution reopen conditions.

## 7. Revised programme phases

The post-Constitution sequence is now:

```text
Phase 5   Constitution v1
Phase 6   Core/Core_Law epistemic-role audit
Phase 7   choose next domain
Phase 7.5 Pre-framework recovery + Material Re-entry + Domain Reconstruction Framework v0.1
Phase 8   one bounded deep well
Phase 9   productive-adequacy review
Phase 9.5 Domain Framework writeback
Phase 10  next domain, or cross-domain synthesis only after at least two deep wells have independently produced usable results
```

The single-well discipline remains.

Adding a domain framework does not authorize parallel deep-well execution.

---

## 8. Cross-domain synthesis boundary

Domain Reconstruction Frameworks make later synthesis more disciplined because they provide an intermediate comparison unit.

**Threshold:** framework writeback is allowed after each deep well, but cross-domain synthesis remains blocked until at least **two** deep wells have independently produced usable results, preserving the existing Execution Plan Phase-10 gate.

Future synthesis should compare, for example:

```text
repeated problem families
repeated objectification losses
repeated bearer / history separations
repeated consequence-attribution failures
repeated translation-only outcomes
repeated domain-specific divergences
```

But cross-domain recurrence is still an empirical/programmatic result, not something inserted into every framework in advance.

## 10. Success condition for the new layer

The Domain Reconstruction Layer is doing real work only if it can answer all of the following before a new deep well begins:

```text
What does this field treat as given?
How do the six Constitution operations translate here?
What objectification choices matter?
Who/what occupies which bearer / measurement / consequence roles?
What stable problem families result?
Where do inherited SRT files belong now?
Where do high-value SourceCards / patches / hooks belong now?
What mature field traditions already own nearby distinctions?
Which one bounded deep well is worth paying for next?
```

If a framework cannot answer these without immediately turning into a literature dump or a domain axiom system, it has failed its role and should be simplified.
