# GRG Dialogue Continuity + Two-Sided Objectification Reconstruction Protocol v0.1

## 0. Purpose

This protocol repairs a specific failure exposed by the 2026-09-23 long dialogue:

```text
source-native first
```

is not sufficient if the next-session handoff has already preselected what the source is expected to reveal.

It also repairs a second failure:

```text
current GRG terms = revisable coordinates
```

is not sufficient if those coordinates are only revised **after** a new grammar candidate has already been extracted.

The stronger method is:

> reconstruct the source **and** reconstruct why current GRG cuts exist before granting a new GRG candidate.

This protocol is a noncanonical method companion.

It does not replace:

- GRG v0.3;
- GTS v0.2;
- M0–M5 / XG1–XG5;
- the #1040 cross-objectification architecture;
- canonical SRT owners.

It constrains how those surfaces are re-entered after a long-dialogue continuity failure.

## 1. Authority / retrieval-value separation

Use the existing repository axes:

- epistemic authority;

Do not create a fourth repository-wide continuity metadata axis.

### 1.1 Epistemic authority

Use only:

- A0-Q;

### 1.2 Retrieval value after author acceptance

Default rule:

> author-accepted / author-approved / author-continued machine analysis is required continuation context unless a later controlling record explicitly narrows, rejects, retires or supersedes it.

This does not change authority:

```text

can coexist with

```

The labels `canonical: false`, `parked`, `downstream`, `companion` and support-only routing do not by themselves demote accepted analysis.

## 2. Long-dialogue writeback rule

A long dialogue is not considered safely written back merely because:

- an author-adjudication record exists;
- a template exists;
- a summary exists;
- a handoff exists.

Minimum safe writeback:

```text
author events
+
visible derivation
+
execution artifacts
+
supersession / reviewer corrections
+
future-session retrieval order
```

The derivation must preserve:

- why a question arose;
- what alternative framing was rejected;
- what conceptual move changed the next question;
- what remained OPEN;
- what later review narrowed or corrected.

## 3. Handoff anti-compression rule

A handoff is an execution instruction surface. It must not silently narrow the source-discovery space.

Forbidden first-contact handoff form:

```text
Study domain D and determine:
- which source item is reach
- which source item is Selection
- which source item is retention
- which source item is proxy
- which source item is higher-order formation
```

Also unsafe:

```text
source-native first
+
a detailed list of expected GRG/SRT-shaped findings
```

Preferred first-contact form:

```text
1. reconstruct the source's own process / mechanism / formal structure;
2. identify its own units, boundaries, distinctions and dependencies;
3. state unresolved handoffs / overloaded objects / alternative cuts in source terms;
4. only then load the GRG self-reconstruction audit.
```

Current GRG concepts may be declared as **lens provenance**.

They may not be specified as expected outputs.

## 4. two-sided objectification reconstruction principle

Every discovery case has two explanandum surfaces.

### 4.1 Source-side explanandum

For each load-bearing source objectification:

- why does the source use this object / variable / boundary?
- what problem does it solve?
- what distinction does it preserve?
- what does it aggregate / background?
- what alternative cuts exist?
- what consequence would expose its limit?

### 4.2 GRG-side explanandum

For each current GRG cut that becomes relevant:

- why did GRG introduce this cut?
- which earlier source / dialogue burden made it useful?
- what distinctions did it compress?
- what does it make operable?
- what current owner already defines / constrains it?
- what would force it to split, merge, demote, disappear or remain source-local?

Hard guard:

> a current GRG cut may act as a probe, but it may not escape becoming an explanandum.

## 5. Discovery sequence

### Stage 0 — source-native recovery

Use source vocabulary and mature source organization.

Record:

- concepts;
- formalisms;
- process units;
- causal / statistical / structural relations;
- controversies;
- negative cases;
- scale / boundary choices;
- source uncertainty.

No GRG candidate.

No GRG mapping.

### Stage 1 — source objectification genealogy

For each load-bearing source cut:

```text
what problem / intervention / measurement burden produced it?
what does it stabilize?
what distinctions does it compress?
what alternative source-native cut exists?
what failure / anomaly reopens it?
```

If the source does not provide a historical genealogy, distinguish:

- source-established function of the cut;
- analyst reconstruction of why the cut is useful.

Do not invent historical intent.

### Stage 2 — domain-native generative reconstruction

Write the process / dependency graph without proprietary GRG labels.

The account should remain intelligible if all GRG terms are deleted.

Prompts may include:

- what differences exist or are generated?
- under what relations do they become consequential?
- what changes accessibility / expression / propagation / retention?
- what transformations occur?
- what later conditions are changed?
- where do mature source models hand off?

These prompts are non-exhaustive and must not become a universal ontology checklist.

### Stage 3 — source coherence / missing-relation search

Ask:

- are two mature source models adjacent but disconnected?
- is one source object carrying multiple intervention-sensitive roles?
- does one model hold fixed a relation another treats as generated?
- does a legitimate recut change attribution?
- is any “missing relation” already owned by a mature source theory?

Allowed result:

`NO MISSING RELATION FOUND`.

### Stage 4 — GRG lens provenance

Only after Stages 0–3, declare:

```text
which current GRG questions motivated attention?
which source relations were visible independently?
which source reconstruction would still exist without GRG?
what alternative lens could have organized the source?
```

This stage exposes bias; it does not validate the GRG lens.

### Stage 5 — reconstruct relevant GRG cuts as explananda

For each GRG term that now appears useful, run:

```text
GRG cut:
existing owner:
original burden / provenance:
what it compresses:
what it distinguishes:
what this source reveals:
```

Then choose one **GRG-cut action**:

- `RETAIN`;
- `SPLIT`;
- `MERGE`;
- `DEMOTE`;
- `DELETE`;
- `SOURCE_LOCAL`;
- `INSUFFICIENT_EVIDENCE`.

These actions describe what happens to the current GRG cut. They are separate from the owner-overlap result vocabulary in Stage 6.

Do not create a new GRG term merely because a current term splits.

### Stage 6 — existing-owner semantic absorption

Before naming a new grammar candidate, compare the exact proposed burden against:

- GRG v0.3;
- relevant 2026-09-22 source-level owners;
- GTS composition / relation patterns;
- active canonical owners where the term touches SRT;
- strongest mature source-native comparator.

Use the existing programme language plus two explicit result states:

- `INHERIT` — an existing GRG owner already carries the relevant burden;
- `REALIZATION` — the source supplies a domain-specific realization of an inherited burden;
- `REORGANIZATION` — the source forces the existing GRG cut / decomposition to change;
- `NO_GRG_GAIN` — mature source theory / current GRG owners absorb the useful result;
- `RESIDUAL_CANDIDATE` — a nontrivial burden remains after all prior checks.

Only `RESIDUAL_CANDIDATE` opens Stage 7.

Do not use `CALIBRATION` as a generic disposition here; that term already has a programme-level meaning in the framework-vs-calibration route.

### Stage 7 — grammar candidate extraction

A new candidate is permitted only when a nontrivial residual remains after Stage 6.

The candidate must state:

- admission condition;
- exclusion / negative case;
- failure condition;
- declared scope;
- source-local necessities preserved;
- what must survive legitimate re-objectification;
- what is allowed to vary.

Do not name a new candidate simply to summarize a source process.

### Stage 8 — test promotion

If promoted beyond discovery:

- freeze the candidate;
- use a genuinely independent target;
- preserve held-out contamination rules;
- run M4-E0 absorption;
- route through XG / M0–M5;
- preserve failed versions.

### Stage 9 — actuality feedback / GRG recut

After source / test consequences return, ask:

- which GRG neutrality / equivalence assignment failed?
- what distinction regained consequence?
- what must reopen?
- what provenance must be restored?
- is the result a source correction, a GRG correction, or both?

A healthy GRG route must allow:

`NO REUSABLE GRG CANDIDATE`.

## 6. Anti-self-sealing requirement

For every retained / new GRG equivalence, state:

> what sustained source-native difference or future consequence would force this equivalence to fail?

If no answer can be given:

```text
strong GRG status = NOT AVAILABLE
```

Do not escape by moving to a more abstract label.

Do not treat “compatible with GRG” as evidence.

## 7. Objectification-as-explanandum gate — M-level operational rule

This is an M-level operational method rule under the author-approved recovery direction; it is not A1 wording or canonical theory.

Before any new candidate, reviewers must be able to answer:

```text
[ ] source objects were explained as working cuts, not merely listed
[ ] current GRG terms did not define the extraction target
[ ] relevant GRG terms were themselves reconstructed
[ ] current-owner overlap was checked before new naming
[ ] split / delete / source-local outcomes were genuinely available
[ ] no “higher-order operator” was invented where v0.3 / existing owners already carry the burden
```

If any of the first four fail:

`STOP NEW GRG CANDIDATE`.

## 8. Continuity review after every major session

For a session that materially changes direction, write back:

### 8.1 Author event

Direct author wording / accepted choice.

### 8.2 Visible derivation

The substantive analysis that made the choice intelligible.

### 8.3 Correction ledger

What earlier analysis was:

- retained;
- narrowed;
- superseded;
- reviewer-corrected.

### 8.4 Execution artifact

Template / protocol / case / experiment if any.

### 8.5 Next-session retrieval route

Must identify:

- LOAD_BEARING records;
- active execution object;
- HOLD items;
- forbidden shortcuts.

Do not reduce the handoff to a list of target-domain correspondences.

## 9. Fresh-session acceptance test

Before starting the next domain, a fresh session should be able to explain:

1. GRG is not a universal object dictionary.
2. GRG itself is a revisable objectification / epistemic proxy.
3. Objectification is useful because it enables operable higher-order re-entry.
4. Reconstructibility prevents that closure from becoming irreversible.
5. Cross-domain unification is a revisable neutrality assignment, not identity.
6. Current GRG terms are probes and explananda.
7. Source-native difference can force GRG recutting.
8. A candidate must survive existing-owner absorption before being called new.
9. #1040 is a useful partial anti-mapping method, not the whole recovered dialogue.
10. #1039 remains HOLD until re-entered under this protocol.

If not, the session has not reconstructed the continuity package.
