# GRG Cross-Objectification Generative Architecture v0.1

> Role: noncanonical **method companion** to the current v0.3 foundational proto-grammar.
>
> This file does not replace v0.3, GTS v0.2, canonical SRT, STATUS routing, or the M0–M5 / XG1–XG5 maturity machinery.
>
> Its purpose is to prevent fusion / domain work from degenerating into object-to-object vocabulary mapping.

## 0.0 Dialogue-continuity corrigendum

This v0.1 architecture remains a valid **first-level anti-object-mapping correction**.

It is **not** the complete continuity owner for the long 2026-09-23 dialogue.

The later recovery established an additional burden:

> current GRG terms / formalisms are not only revisable coordinates used to probe a source; they are also historically formed objectifications that must themselves become explananda.

Therefore this file must now be used together with:

`Operations/Proposals/SRT_GRG_DIALOGUE_CONTINUITY_DUAL_RECONSTRUCTION_PROTOCOL_V0_1_2026-09-23.md`.

Before Stage 5 may create a new grammar candidate, the recovery protocol requires:

1. source-objectification genealogy;
2. domain-native generative reconstruction;
3. GRG-objectification genealogy / dual reconstruction;
4. existing-owner semantic absorption;
5. only then a decision about whether a nontrivial new candidate remains.

Stage 7 below remains useful as a late mapping audit, but it is **not the first point at which GRG itself is allowed to be explained, split, demoted or deleted**.

Hard guard:

~~~text
GRG working objectification
= probe + explanandum
!= source extraction target
~~~

## 0. Compact correction

~~~text
WRONG RESEARCH ENGINE

domain object / term
-> find GRG object / term
-> score correspondence
-> infer grammar

RIGHT RESEARCH ENGINE

source-native models / concepts / formalisms
-> make their objectification assumptions explicit
-> re-cut / re-objectify where warranted
-> reconstruct generative relations in source-native terms
-> ask whether separated mature models become more coherent
-> identify missing / hidden / overloaded relations
-> only then abstract a revisable grammar candidate
-> only after freezing a candidate, test cross-objectification survival / gain
-> use GRG mapping labels late as audit / bookkeeping
~~~

Object correspondence is optional.

Generative constraint is the research target.

## 1. Three analytically distinct surfaces

### 1.1 Domain objectification

A domain already stabilizes research through:

- units;
- variables;
- equations;
- state spaces;
- categories;
- causal mechanisms;
- measurement conventions;
- boundaries and scales.

These can be excellent cuts. Do **not** assume in advance that every mature domain object hides an error or needs decomposition.

Question:

> What does this objectification distinguish, stabilize, aggregate, leave implicit or make operable for the source's own problem?

### 1.2 GRG working objectification

Current GRG terms and future formalisms — for example generative condition, reach, support, proxy, reconstruction, order, GTS — are working cuts.

They are:

~~~text
revisable research coordinates
!= universal domain entities
!= required cross-domain vocabulary
!= final ontology inventory
~~~

A source is allowed to make a GRG distinction unnecessary, split it, combine it, or force a new cut.

### 1.3 Grammar candidate

A grammar candidate is not "the hidden object behind both vocabularies".

It is a proposed organization of relations / constraints that:

- can be stated without requiring one-to-one term identity;
- survives at least some legitimate re-objectification;
- retains admission / exclusion / failure conditions;
- remains source-native compatible;
- is nontrivial enough to constrain later analysis.

This is an inferential research object, not a God-view layer.

## 2. GRG's domain task

GRG domain work asks:

> Can source-native models be reorganized so their generative dependencies become more coherent, and does that reorganization expose a missing relation, hidden dependency, overloaded objectification, new failure boundary, or new question?

It does **not** require:

~~~text
domain X has a "reach" object
domain Y has a "support" object
domain Z has a "proxy" object
biological selection = SRT Selection
money = GRG proxy
fitness = GRG variable Q
~~~

Those may sometimes be useful local mappings, but they are not the method.

A successful case may have:

~~~text
GRG object correspondence:
  NONE

domain generative reconstruction:
  USEFUL
~~~

## 3. Discovery mode vs test mode

### 3.1 Discovery mode

Use when the aim is grammar formation / revision.

Required:

- source-native fidelity;
- explicit objectification boundary;
- alternative legitimate cuts where available;
- GRG lens declaration;
- relation reconstruction that remains intelligible without unexplained GRG vocabulary;
- explicit projection-risk check;
- failed / empty mappings preserved.

Allowed:

- change GRG terms;
- split or delete GRG fields;
- generate new relation candidates after source inspection;
- conclude that a domain organization is already superior to the current GRG cut.

Not allowed:

- call post-hoc recurrence independent evidence;
- upgrade to M3/M4 because the reconstruction is attractive;
- count vocabulary match as support.

### 3.2 Test mode

Use when claiming that a grammar candidate has survived beyond the discovery case.

Before decisive held-out inspection, freeze:

~~~text
candidate relation / burden
scope
unit / boundary / grain
what must survive legitimate re-objectification
admission condition
exclusion / negative case
failure condition
strongest mature baseline
prospective discrimination, if any
~~~

Then route to existing:

- XG1–XG5;
- M3 / M4;
- M4-E0 absorption;
- GTS where a bounded transformation is available.

Freeze the **relation claim**, not a mandatory GRG vocabulary word.

## 4. Cross-objectification reconstruction sequence

### Stage 0 — source-native recovery

Record the domain's own:

- concepts;
- models;
- equations;
- mechanism claims;
- controversies;
- known boundaries;
- strongest mature explanations.

No GRG gain claim yet.

### Stage 1 — objectification declaration

For each load-bearing source object / formal variable ask:

~~~text
what problem does it solve?
what unit / boundary / grain does it stabilize?
what relations does it make explicit?
what relations does it aggregate or leave implicit?
what alternatives are recognized inside the domain?
~~~

Do not assume "compression" means "defect".

### Stage 2 — legitimate re-objectification

Where source practice permits, examine alternative:

- scales;
- partitions;
- causal decompositions;
- state representations;
- process / outcome separations;
- boundary choices;
- coordinate descriptions.

Purpose:

> distinguish a robust generative dependency from an artifact of one convenient cut.

### Stage 3 — domain-native generative reconstruction

Write the process / relation organization first in source-native or neutral language.

Questions may include:

~~~text
what differences / conditions are present?
what makes a difference consequence-bearing?
what dependencies modulate that consequence?
what transformation actually occurs?
what changes later constraints / accessibility / boundaries?
what prior organization enters later generation?
where do separate mature submodels hand off to each other?
~~~

These are prompts, not a universal mandatory field list.

### Stage 4 — coherence and missing-relation search

Ask:

- Do two mature source models describe adjacent parts of one process but leave their interface implicit?
- Does one source variable combine multiple generative roles that matter differently under intervention?
- Does an existing model treat as fixed a relation another source model shows can be generated / dissolved?
- Does a legitimate recut change causal attribution without changing the realized process?
- Is there a missing dependency needed to make the combined account internally coherent?

A missing relation is a candidate research gain only after mature-neighbor absorption is checked.

### Stage 5 — grammar candidate extraction

Only now abstract a candidate.

Preferred form:

~~~text
when [declared relation / condition],
then [declared generative dependency],
such that [admission / exclusion structure],
and failure occurs when [failure condition].
~~~

Avoid extracting merely:

~~~text
state -> transition -> state
feedback changes future state
history matters
everything changes possibilities
~~~

unless a nontrivial constraint makes the claim stronger.

### Stage 6 — test promotion

If a candidate is promoted beyond discovery:

- freeze it;
- choose a genuinely independent / held-out realization;
- specify legitimate re-objectification stress;
- run source-native and absorption checks;
- route through XG / M-levels.

### Stage 7 — late mapping audit

Only after reconstruction may the case ask:

- does a current GRG term conveniently name part of this relation?
- should that term be split / dropped / retained?
- what non-identity guard is needed?

Mapping count gives no positive maturity credit.

## 5. Failure architecture

### F1 — source failure

The source claim / evidence is insufficient for the reconstruction.

### F2 — grammar mismatch

A frozen grammar candidate is not present in the source-native organization.

### F3 — re-objectification failure

The candidate disappears or changes meaning under legitimate alternative cuts that it claimed to survive.

### F4 — projection failure

The "relation" exists only after GRG vocabulary is imposed; the source-native account does not independently support it.

### F5 — triviality failure

The claim reduces to generic dynamics, generic feedback, generic history, generic state transition or an unrestricted "everything affects later possibilities".

### F6 — absorption / no-gain result

The mature domain already owns the same useful distinction / integration / control / failure burden in materially the same form.

This may still be a successful source reconstruction, but:

~~~text
GRG incremental gain = NO / ABSORBED
~~~

### F7 — prospective failure

A frozen prediction / diagnostic / intervention distinction does not survive the held-out target.

## 6. Failure does not become support by revision

A self-revising grammar must preserve failed versions.

~~~text
candidate G_n fails
-> revise / split / withdraw
-> candidate G_(n+1)

G_(n+1) may later succeed

but

G_(n+1) success
does not retroactively support G_n.
~~~

Held-out contamination rule:

~~~text
if target T contributed to the failure / diagnosis / revision of G_n,
then T is no longer held-out for G_(n+1).

G_(n+1) requires a new independent target for M3 / M4-style confirmation.
~~~

This is the core anti-self-sealing rule.

## 7. Formalization rule

Future GRG formalization is permitted as a working objectification.

Do not use it as a cross-domain variable dictionary.

~~~text
GRG symbol R
-/>
every domain contains a variable called / functioning as R

GRG equation F
-/>
every source model should be rewritten into F
~~~

A mature formal grammar should aim to encode relation constraints that survive specified recuts.

If a domain forces a different unit, topology, variable family or process decomposition, revise the GRG formalization rather than inventing a false source counterpart.

Formalization remains subject to the repository's no-God-view / objectification reflexivity guards.

## 8. Relation to v0.3 scientific gain

This architecture does not replace v0.3 §12.1.

It clarifies the upstream route into it.

~~~text
DISCOVERY
-> candidate relation formed / revised
-> candidate frozen
-> independent / held-out test

then, if claimed:

XG1 independent source-native grounding
XG2 shared generative burden survives mechanism change
XG3 admission / exclusion / failure constraints survive
XG4 source necessities are not flattened
XG5 prospective discrimination survives absorption

separate objectification-stress question:
  does the candidate remain intelligible / constraint-preserving under legitimate alternative cuts?
  this is NOT a substitute for XG2 mechanism change
~~~

Maturity remains:

~~~text
M0 resemblance
M1 analogy
M2 burden-aligned candidate
M3 independently evidenced frozen relation
M4 transfer-generating + absorption-resistant gain
M5 repeatedly cross-domain constrained grammar candidate
~~~

## 9. Relation to GTS and Fusion-Case Card

### GTS

GTS v0.2 remains the primary bounded transformation record.

This architecture supplies the **pre-GTS / cross-objectification reconstruction route** when the correct transformation / cut is not yet stable.

Once a bounded transformation is clear, use GTS.

### Fusion-Case Card

The Fusion-Case Card remains useful for:

- source / GRG non-identity;
- mapping disposition;
- failure / empty-field preservation;
- late schema pressure;
- maturity separation.

But it is not the research engine.

New default sequence:

~~~text
source-native reconstruction
-> Cross-Objectification Reconstruction Record
-> domain-native generative organization
-> coherence / missing-relation search
-> candidate grammar extraction
-> test-mode freeze where warranted
-> GTS / XG / M-level test where warranted
-> Fusion-Case Card late audit / schema feedback
~~~

## 10. Minimum grammar-gain question

Before calling a reconstruction a GRG gain, answer:

> If all GRG proprietary labels are removed, what source-checkable relation, distinction, integration, failure condition, question or prospective intervention remains that was made clearer or newly testable by this reconstruction?

If the answer is only a vocabulary substitution:

~~~text
REDESCRIPTIVE_ONLY / PAYOFF NOT ESTABLISHED
~~~

## 11. Scope boundary

This architecture does not:

- close the live latent-reconstructive-reach route;
- claim that the evolution case validates a grammar candidate;
- authorize a third fusion case merely to rescue a preferred term;
- replace the current foundation owner;
- create v0.4;
- rewrite canonical SRT;
- weaken source-native-first;
- turn "grammar" into an unfalsifiable residual after every failed mapping.
